# 1. Dockerfile 개요

## 1.1 Dockerfile 개념 및 도입 배경

### 1.1.1 Dockerfile
- Dockerfile은 애플리케이션을 컨테이너화하는 데 필요한 베이스 이미지 [^1] 지정, 런타임 종속성 설치, 소스코드 파일 복사, 환경 변수 선언, 구동 명령 등을 텍스트 형식으로 명시한 자동화 빌드 명세서.
- `docker build` 명령어를 수행하면 도커 데몬(Docker Daemon)이 Dockerfile에 정의된 명령 지시어를 위에서 아래로 순차 해석하여 컨테이너 이미지를 생성함.
- Dockerfile 예시
  ```dockerfile
  # 1. 베이스 이미지 지정 (Alpine Linux 3.24.1)
  FROM alpine:3.24.1

  # 2. 컨테이너 내부 작업 디렉터리 설정
  WORKDIR /app

  # 3. 런타임 환경 변수 선언
  ENV APP_ENV=production

  # 4. 웹 서버(Nginx) 패키지 설치 및 파일 복사(https://pkgs.alpinelinux.org/packages 에서 패키지 버전 확인)
  RUN apk update && apk add --no-cache nginx=1.31.4
  COPY index.html /usr/share/nginx/html/index.html

  # 5. 수신 포트 명세 및 포그라운드 구동 명령 지정
  EXPOSE 80
  CMD ["nginx", "-g", "daemon off;"]
  ```

### 1.1.2 인프라 구축 방식의 패러다임 전환
- 전통적 수동 구축 방식: 시스템 관리자가 서버 OS에 직접 접속하여 쉘 스크립트 실행이나 패키지 명령을 수동으로 실행함. 이로 인해 작업자 간 설정 오차, 환경 문서화 누락, 런타임 버전 파편화 및 불일치 문제가 발생함.
- Dockerfile 기반 자동화 방식: 인프라 구성을 코드로 명시하는 코드로서의 인프라(IaC, Infrastructure as Code) 개념을 실현함. 인프라 명세 자체가 버전 관리 시스템(Git)에 의해 관리되므로 환경 구축 과정이 동일하게 재현됨.

## 1.2 Dockerfile 핵심 구성 요소 및 레이어 메커니즘

### 1.2.1 Dockerfile 지시어 (Instructions)
- Dockerfile 내에서 이미지를 생성하기 위한 동작을 도커 데몬에 전달하는 대문자 텍스트 명령 키워드.
- 베이스 이미지 지정(`FROM`), 패키지 설치 및 명령어 실행(`RUN`), 파일 복사(`COPY`), 런타임 환경 변수 선언(`ENV`), 컨테이너 구동 시 기본 실행 명령(`CMD`) 등으로 구성됨.
- 작성된 각 지시어는 이미지 빌드 시 하나의 독립된 층(Layer)을 형성하는 기본 단위로 작동함.

### 1.2.2 이미지 레이어 (Image Layer)
- 도커 이미지는 단일 통째 파일이 아니라, 여러 개의 읽기 전용(Read-Only) 파일시스템 스냅샷 [^2] 인 레이어가 차곡차곡 쌓여 완성되는 유니온 파일시스템 [^3] (Union File System) 구조.
- Dockerfile에서 런타임 환경을 변경하는 주요 지시어(`FROM`, `RUN`, `COPY`, `ADD` 등)가 실행될 때마다 이전 레이어 위에 새로운 읽기 전용 레이어가 커밋되어 중첩 저장됨.
- 동일한 베이스 이미지나 라이브러리 레이어는 여러 다른 이미지 간에 물리적으로 공유되므로 디스크 공간을 절약하고 다운로드 속도를 향상시킴.

### 1.2.3 부모 레이어 체인과 캐시 무효화 원리
- 각 레이어는 독립적으로 분리되어 임의 재사용되는 것이 아니라, 1단계(`FROM`)부터 상위 단계까지 부모 레이어의 해시 체인으로 결합된 순차적 누적 구조.
- 1단계부터 현재 단계까지 부모 레이어와 지시어 내용(명령어 구문 및 파일 해시 등)이 완전히 일치할 때만 캐시(`Using cache`)가 재활용됨.
- 중간 단계에서 변경이 발생하여 캐시 미스(Cache Miss)가 일어나면, 해당 단계를 포함하여 이후의 모든 하위 레이어 캐시는 전면 무효화(Cache Invalidation)되어 새로 실행 및 커밋됨.

### 1.2.4 컨테이너 레이어와 Copy-on-Write (CoW) 원리
- 이미지 전체 파일시스템의 컨테이너 내부 복사 배제
    - 컨테이너가 구동(`docker run`)될 때 이미지 데이터 전체가 물리적으로 복사되는 것이 아니라, 하위의 읽기 전용 이미지 레이어들을 그대로 공유 참조(Union Mount)하는 구조.
    - 컨테이너 구동 시점에는 최상단에 수 KB 크기의 얇은 읽고 쓰기 가능 컨테이너 레이어(Writable Layer)만 새로 추가됨.
- 파일 수정 시의 Copy-on-Write (CoW) 동작
    - 컨테이너 내부에서 기존 읽기 전용 레이어에 존재하는 파일을 수정할 경우, 도커는 해당 파일만 최상단 컨테이너 레이어로 복사하여 수정하는 Copy-on-Write 방식을 적용함.
    - 이에 따라 하위 이미지 레이어의 원본 파일은 변경되지 않고 유지되며, 컨테이너가 파기되더라도 원본 이미지 레이어는 안전하게 보존됨.

## 1.3 전통적 배포 방식과 Dockerfile 기반 방식의 비교

### 1.3.1 환경 명세의 표준화 및 격리성
- 전통적 배포 환경에서는 호스트 OS에 종속된 라이브러리 및 환경 변수 충돌로 인해 다중 애플리케이션 공존이 제한적임.
- Dockerfile을 통한 빌드 방식은 독립된 파일시스템과 실행 격리 환경을 보장하는 이식성 높은 전용 이미지를 생성함.

### 1.3.2 협업 체계 및 검증 효율성
- 개발, 검증(QA), 스테이징, 운영 환경 전반에 걸쳐 유효성이 검증된 인프라 템플릿(Dockerfile) 하나로 동일한 이미지 생성을 보장함.
- 새로운 개발 인원이 팀에 합류하더라도 단일 `docker build` 실행만으로 복잡한 개발 환경 세팅을 수 초 내에 자동 완성함.

## 1.4 Dockerfile 빌드 파이프라인 동작 원리

### 1.4.1 빌드 컨텍스트 (Build Context) 전송
- 도커 클라이언트와 데몬 간 작업 디렉터리 압축 전송
    - 사용자가 `docker build` 명령을 입력하면 도커 클라이언트는 지정된 작업 디렉터리 내부의 모든 파일과 하위 폴더를 압축하여 도커 데몬 서비스로 전송함.
    - 도커 데몬은 전달받은 압축 파일을 바탕으로 이미지를 빌드하며, 이 전송 데이터 영역을 빌드 컨텍스트 [^5] (Build Context)라 부름.
- 파일 접근 허용 경계선 역할 및 제외 처리
    - Dockerfile 내의 `COPY` 및 `ADD` 지시어는 오직 빌드 컨텍스트에 포함되어 전달된 파일만 이미지로 복사할 수 있으며, 이 영역 바깥의 호스트 파일에는 접근할 수 없음.
    - 작업 디렉터리 내에 불필요한 대용량 파일이 포함되어 빌드가 지연되는 것을 방지하기 위해 `.dockerignore` 파일을 활용하여 전송 대상에서 선제적으로 제외함.
    - `.dockerignore` 파일 예시
      ```gitignore
      # 1. 모든 파일/폴더를 전송 대상에서 제외
      *
      # 2. 오직 JAR 결과물과 Dockerfile만 예외로 전송 대상에 포함
      !build/libs/*.jar
      !Dockerfile
      ```
- 최신 BuildKit 빌드 엔진의 지능형 전송 (Lazy Transfer) 메커니즘
    - 최신 BuildKit 엔진은 Dockerfile 구문을 미리 분석하여 `COPY` 등에 지정된 대상 파일의 해시(Checksum)만 지능적으로 추적 및 최소 전송하므로, 지정되지 않은 주변 파일이 변경되어도 캐시가 유지됨.
    - 다만, `COPY . .` 구문 사용 시의 캐시 파기 방지, 초기 파일 상태(Stat) 스캔 지연 차단, 민감 정보 유출 방지를 위해 `.dockerignore` 작성은 여전히 필수적인 모범 사례로 다뤄짐.

### 1.4.2 지시어 해석 및 캐싱 기반 레이어 커밋
- 임시 컨테이너 구동을 통한 명령 실행 및 레이어 커밋
    - 도커 이미지는 읽기 전용(Read-Only)이므로 이미 지어진 레이어 내부에서는 리눅스 명령(`RUN` 등)을 직접 실행하거나 파일을 변경할 수 없음.
    - 이에 따라 도커 데몬은 이전 레이어 위에 쓰기 가능한 '임시 컨테이너'를 구동하고, 그 격리된 작업 공간 안에서 지시어 명령을 실행함.
    - 명령 실행이 완료되면 변경된 파일시스템 상태만 새로운 읽기 전용 레이어로 스냅샷 [^2] 커밋(`docker commit`)한 뒤 임시 컨테이너를 파기함.
- 캐시 적중을 통한 빌드 속도 최적화
    - 1단계부터 상단 지시어 구문 및 파일 내용이 완전히 동일할 경우, 도커 데몬은 이전 빌드에서 생성된 레이어 캐시 [^6] 를 자동으로 재활용(`Using cache`)하여 중복 실행을 스킵하고 빌드 시간을 단축함.

# 2. Dockerfile 주요 지시어 명세

- 공식 문서: [Docker Docs - Dockerfile reference](https://docs.docker.com/reference/dockerfile/)

| 지시어 (Instruction) | 설명 (Description) |
| --- | --- |
| [ADD](https://docs.docker.com/reference/dockerfile/#add) | 로컬 파일·디렉터리 복사, 원격 URL 파일 다운로드 및 압축 자동 해제. |
| [ARG](https://docs.docker.com/reference/dockerfile/#arg) | 이미지 빌드 시점에 사용할 빌드 변수 정의. |
| [CMD](https://docs.docker.com/reference/dockerfile/#cmd) | 컨테이너 실행 시 수행할 기본 명령어 또는 인자 지정. |
| [COPY](https://docs.docker.com/reference/dockerfile/#copy) | 호스트의 파일이나 디렉터리를 컨테이너 내부로 복사. |
| [ENTRYPOINT](https://docs.docker.com/reference/dockerfile/#entrypoint) | 컨테이너 시작 시 실행할 기본 명령어(고정 실행 파일) 지정. |
| [ENV](https://docs.docker.com/reference/dockerfile/#env) | 컨테이너 런타임 환경 변수 설정. |
| [EXPOSE](https://docs.docker.com/reference/dockerfile/#expose) | 컨테이너가 바인딩하여 수신 대기할 포트 번호 명세. |
| [FROM](https://docs.docker.com/reference/dockerfile/#from) | 베이스 이미지 지정 및 새로운 빌드 스테이지 생성. |
| [HEALTHCHECK](https://docs.docker.com/reference/dockerfile/#healthcheck) | 컨테이너의 정상 동작 상태를 주기적으로 검증. |
| [LABEL](https://docs.docker.com/reference/dockerfile/#label) | 이미지에 작성자, 설명 등의 메타데이터 추가. |
| [MAINTAINER](https://docs.docker.com/reference/dockerfile/#maintainer-deprecated) | 이미지 작성자 정보 명세 (현재는 권장되지 않으며 LABEL 사용). |
| [ONBUILD](https://docs.docker.com/reference/dockerfile/#onbuild) | 해당 이미지를 베이스 이미지로 재사용할 때 실행할 트리거 지시어 설정. |
| [RUN](https://docs.docker.com/reference/dockerfile/#run) | 이미지 빌드 중 리눅스 셸 명령어 실행 및 새로운 레이어 생성. |
| [SHELL](https://docs.docker.com/reference/dockerfile/#shell) | 명령어 실행 시 사용할 기본 셸 프로그램 지정. |
| [STOPSIGNAL](https://docs.docker.com/reference/dockerfile/#stopsignal) | 컨테이너 종료 시 전달할 시스템 콜 시그널 지정. |
| [USER](https://docs.docker.com/reference/dockerfile/#user) | 명령어 실행 및 컨테이너 구동 시 적용할 사용자/그룹 계정 설정. |
| [VOLUME](https://docs.docker.com/reference/dockerfile/#volume) | 데이터 지속성 확보를 위한 볼륨 마운트 포인트 선언. |
| [WORKDIR](https://docs.docker.com/reference/dockerfile/#workdir) | 컨테이너 내부의 작업 기준 디렉터리 설정 및 이동. |

- Dockerfile 지시어 구성 단계
    - 지시어 배치 구조: 이미지 빌드 라이프사이클(기반 환경 설정 -> 파일 복사 -> 빌드/환경 설정 -> 런타임 명세)의 흐름에 따라 4단계로 구분함.
    - 레이어 캐시 최적화: 변경 빈도가 낮은 베이스 환경 및 복사 지시어를 상단에 배치하고, 자주 변경되는 빌드/환경 설정 및 런타임 지시어를 후반부에 배치하여 도커 레이어 캐시 활용도를 향상시킴.

## 2.1 기반 환경 설정 (`FROM`, `LABEL`, `WORKDIR`)

### 2.1.1 베이스 이미지 선언 (`FROM`)

- 개념 및 특징
    - 이미지 빌드 시 기준이 되는 베이스 이미지를 지정함.
    - Dockerfile 내에서 가장 먼저 선언되어야 하며, 특정 버전을 의미하는 태그(예: `alpine:3.24.1`, `eclipse-temurin:25-jdk-alpine`)를 명시하여 빌드 환경의 재현성을 보장함.
- 가변 태그(Mutable Tag) 사용 시 주의사항
    - 가변 태그 위험성: `FROM nginx:1.31`나 `FROM alpine:latest`와 같이 버전 범위가 넓은 태그를 사용할 경우, 원격 레지스트리의 최신 이미지 갱신 상태에 따라 빌드 시점마다 서로 다른 베이스 이미지 레이어가 다운로드될 위험이 존재함.
    - 환경 불일치 발생 원인: 로컬 개발 환경에서는 이전에 다운로드되어 캐시된 베이스 이미지(예: `1.31.3` 기준)를 계속 재활용하는 반면, 캐시가 비어있는 운영 서버에서는 원격 레지스트리의 최신 베이스 이미지(예: `1.31.4` 기준)를 새로 다운로드받게 됨.
    - 장애 파급 효과: 이로 인해 개발 환경에서는 정상 작동하던 애플리케이션이 운영 배포 시점에 버전 차이로 인한 런타임 오류를 일으키는 개발-운영 환경 불일치 문제가 초래됨.
    - 명세 모범 사례: 실무에서는 패치 버전까지 명확히 고정된 태그(`FROM nginx:1.31.4`)를 사용하거나, 이미지 고유 해시값(`FROM nginx@sha256:a1b2c3...`)을 선언하여 모든 환경에서 100% 동일한 베이스 이미지 사용을 보장함.

```dockerfile
# 베이스 이미지 지정 (Alpine Linux 3.24.1 고정 버전 사용)
FROM alpine:3.24.1
```

```bash
# FROM 지시어 기반 단독 빌드
docker build -t ch02-01-from-image .
```

### 2.1.2 이미지 메타데이터 표기 (`LABEL`)
- 도커 이미지에 작성자(Maintainer), 버전(Version), 라이선스, 프로젝트 설명 등 키-값(`KEY="VALUE"`) 형태의 메타데이터를 수록함.

```dockerfile
# 베이스 이미지 지정
FROM alpine:3.24.1

# 이미지 메타데이터 명세
LABEL maintainer="kilyong <kilyong@example.com>"
LABEL version="1.0.0"
LABEL environment="production"
LABEL description="Spring Board Nginx Web Server Image"
```

```bash
# 2. LABEL 명세 이미지 빌드
docker build -t ch02-01-label-image .

# 전체 LABEL 메타데이터 정보 검증 (JSON 포맷 출력)
docker inspect --format='{{json .Config.Labels}}' ch02-01-label-image
# 출력 결과: {"description":"Spring Board Nginx Web Server Image","environment":"production","maintainer":"kilyong <kilyong@example.com>","version":"1.0.0"}

# 특정 LABEL key 값 단독 추출 검증 (점 표기법 방식)
docker inspect --format='{{.Config.Labels.version}}' ch02-01-label-image
# 출력 결과: 1.0.0

# 특정 LABEL key 값 단독 추출 검증 (index 함수 방식)
docker inspect --format='{{index .Config.Labels "environment"}}' ch02-01-label-image
# 출력 결과: production

# 특정 LABEL Key=Value 완전 일치(Exact Match) 기반 이미지 필터링 검색
docker image ls --filter "label=environment=production"

# 특정 LABEL Key 유무 기반 컨테이너 필터링 검색 (Key 이름만 지정)
docker ps -a --filter "label=maintainer"

# 특정 LABEL Key=Value 완전 일치 기반 컨테이너 필터링 검색
docker ps -a --filter "label=environment=production"
```

- 이미지 및 컨테이너 상세 정보 추출 문법 (Go Template)
    - 전체 JSON 변환 (`{{json .Config.Labels}}`): 지정한 객체(라벨, 네트워크, 볼륨 등)의 전체 구조 데이터를 가독성 높은 표준 JSON 포맷으로 변환하여 출력함.
    - 단일 속성 점 표기법 (`{{.Config.Labels.version}}`): 특수문자가 없는 단순 영문 속성 키 이름일 경우 점(.) 표기법을 통해 직관적이고 간결하게 단독 추출함.
    - 단일 속성 index 함수 (`{{index .Config.Labels "key"}}`): 속성 키 이름에 점(.)이나 하이픈(-) 등의 특수문자가 포함되어 점 표기법 사용 시 구문 오류가 발생하는 경우 `index` 내장 함수를 사용하여 안전하게 단독 추출함.

### 2.1.3 작업 디렉터리 설정 (`WORKDIR`)
- 컨테이너 내부에서 이후 실행되는 모든 명령어(`RUN`, `CMD`, `ENTRYPOINT`, `COPY` 등)의 작업 기준 디렉터리를 설정함.
- 지정한 디렉터리가 컨테이너 내부에 존재하지 않을 경우 자동으로 생성함.

```dockerfile
# 베이스 이미지 지정
FROM alpine:3.24.1

# 이미지 메타데이터 명세
LABEL maintainer="kilyong <kilyong@example.com>"
LABEL version="1.0.0"
LABEL environment="production"
LABEL description="Spring Board Nginx Web Server Image"

# 내부 작업 디렉터리 생성/이동
WORKDIR /app
```

```bash
# WORKDIR 지정 후 컨테이너 내부 작업 디렉터리(/app) 위치 확인
docker build -t ch02-01-workdir-image .
docker run --rm ch02-01-workdir-image pwd
# 출력 결과: /app
```

## 2.2 파일 복사 (`ADD`, `COPY`)

### 2.2.1 원격 파일 다운로드 및 압축 해제 (`ADD`)
- 호스트 파일 복사 기능뿐만 아니라 원격 URL 파일 다운로드 및 tar 아카이브 자동 압축 해제 기능을 제공함.
- 호스트 로컬의 tar 계열 압축 파일(`.tar`, `.tar.gz`, `.tgz` 등)을 복사할 때만 컨테이너 내부로 자동 압축 해제(Unpack)되며, `.zip` 파일이나 원격 URL로 다운로드받은 파일은 자동 해제되지 않고 파일 그대로 복사됨.
- 의도치 않은 압축 해제 부작용
    - tar 압축 파일 원본 자체를 보관하고 싶은 경우에도 `ADD`는 무조건 압축을 풀어버려 파일 시스템을 어지럽히는 부작용이 발생함.
    - 단순 파일 복사 시에는 `COPY` 지시어를 사용하는 것이 모범 사례로 권장됨.

```dockerfile
# 베이스 이미지 지정 및 호스트의 tar 압축 파일 자동 해제 복사 예시
FROM alpine:3.24.1
WORKDIR /app
ADD sample-data.tar.gz /app/
```

### 2.2.2 소스코드 및 파일 복사 (`COPY`)
- 호스트 시스템의 파일이나 디렉터리를 컨테이너 내부의 지정한 경로로 단순 복사.
- 예측 가능하고 투명한 파일 복사 동작을 보장하므로 `ADD` 대신 `COPY`를 사용하는 것이 모범 사례로 권장됨.
- 다중 파일 복사 및 문법 패턴
    - 단일 COPY 지시어에서 다중 복사: `COPY index.html hello.html /app/` 형태로 여러 대상 파일을 나열하여 단일 레이어로 복사함.
    - 와일드카드 사용: `COPY *.html /app/`과 같이 특정 확장자나 패턴의 파일 모음을 일괄 복사함.
    - 다중 COPY 지시어 나열: `COPY` 지시어를 여러 줄로 나누어 단계별로 나열함. 자주 변경되지 않는 설정 파일(예: `build.gradle`, `package.json`)을 먼저 복사한 후 소스코드를 복사하면 도커 레이어 캐시 활용도를 높일 수 있음.

```dockerfile
# 베이스 이미지 지정, 작업 디렉터리 설정 및 파일 복사
FROM alpine:3.24.1
WORKDIR /app
COPY index.html hello.html /app/
```

```bash
# COPY 지시어 검증 및 컨테이너 내부 복사 파일 목록 확인
docker build -t ch02-02-copy-image .
docker run --rm ch02-02-copy-image ls -la /app
# 출력 결과: index.html 파일 존재 확인
```

## 2.3 빌드 및 환경 설정 (`RUN`, `ENV`, `ARG`)

### 2.3.1 빌드 임시 변수 지정 (`ARG`)

- 개념 및 특징
    - 이미지 빌드 시점(`docker build --build-arg`)에만 한정하여 사용하는 빌드 임시 변수를 선언함.
    - 기본값(Default Value) 설정: `ARG APP_VERSION=1.0.0`처럼 기본값을 지정해두면 빌드 시 인자를 넘기지 않아도 안전하게 빌드되며, `--build-arg` 옵션 전달 시 해당 기본값을 오버라이드(덮어쓰기)함.
    - 최종 런타임 컨테이너 환경에는 유지되지 않으므로 보안 및 빌드 파라미터 전달용으로 활용함.
- 실무 주요 활용 처
    - 애플리케이션 런타임 버전 조회: `ENV APP_VER=$APP_VERSION`으로 연결하여 앱 코드(`System.getenv("APP_VER")`)에서 헬스체크 API 및 로깅 용도로 사용함.
    - 동적 패키지 설치: 설치할 외부 바이너리 버전(`ARG MAVEN_VER=3.9.6`)을 빌드 명령 시점에 자유롭게 교체함.
    - 이미지 메타데이터 표기: `LABEL version=$APP_VERSION` 구문으로 도커 이미지 정보 관리에 활용함.

```dockerfile
# 베이스 이미지 지정 및 빌드 시점 임시 변수 선언 및 활용
FROM alpine:3.24.1
ARG APP_VERSION=1.0.0
ENV APP_VER=$APP_VERSION
```

```bash
# --build-arg 옵션으로 빌드 변수를 주입하여 이미지 빌드 및 런타임 환경 변수 검증
docker build --build-arg APP_VERSION=2.0.0 -t ch02-03-arg-image .
docker run --rm ch02-03-arg-image printenv APP_VER
# 출력 결과: 2.0.0
```

### 2.3.2 런타임 환경 변수 선언 (`ENV`)

- 개념 및 특징
    - 컨테이너 내부 환경 변수를 키-값(`KEY=VALUE`) 쌍으로 선언함.
    - 지정된 환경 변수는 이미지 빌드 과정뿐만 아니라 런타임으로 구동 중인 컨테이너 내부 프로세스에도 지속 반영됨.

```dockerfile
# 베이스 이미지 지정 및 런타임 환경 변수 선언
FROM alpine:3.24.1
ENV PORT=80
ENV ENVIRONMENT=production
```

```bash
# ENV 지정 및 주입 결과 런타임 환경 변수 검증
docker build -t ch02-03-env-image .
docker run --rm ch02-03-env-image printenv ENVIRONMENT
# 출력 결과: production
```

### 2.3.3 이미지 빌드 명령 실행 (`RUN`)

- 개념 및 특징
    - 이미지 빌드 과정 중 지정된 리눅스 쉘 명령어를 실행하고, 그 수행 결과를 새로운 캐시 가능한 이미지 레이어로 커밋함.
    - 주로 필요한 패키지 설치(apt-get, apk 등)나 프로젝트 사전 빌드 작업에 활용함.

```dockerfile
# 베이스 이미지 지정 및 패키지 설치 명령 실행
FROM alpine:3.24.1
RUN apk update && apk add --no-cache nginx=1.31.4
```


## 2.4 런타임 명세 (`EXPOSE`, `CMD`, `ENTRYPOINT`)

### 2.4.1 수신 포트 명세 (`EXPOSE`)

- 개념 및 특징
    - 컨테이너가 런타임에 수신 대기할 대표 네트워크 포트 번호를 명시함.
    - 실제 호스트 포트와 컨테이너 포트를 연결하는 포트 바인딩(포트 매핑)을 직접 수행하지 않으며, 타 개발자 및 도커 데몬을 위한 문서화 목적으로 작성됨.

```dockerfile
# 베이스 이미지 지정 및 80번 포트 수신 대기 선언 (문서화 용도)
FROM alpine:3.24.1
EXPOSE 80
```

### 2.4.2 런타임 구동 명령어 지정 (`CMD`, `ENTRYPOINT`)

- 개념 및 특징
    - `CMD`: 컨테이너 구동(`docker run`) 시 실행할 기본 명령어를 설정하며, 실행 시 전달된 인자에 의해 오버라이드(덮어쓰기)됨.
    - `ENTRYPOINT`: 시작 시 항상 고정하여 실행할 명령어를 설정하며, 전달된 인자를 매개변수로 수신함.

```dockerfile
# 베이스 이미지 지정, Nginx 패키지 설치 및 실행 명령어 지정
FROM alpine:3.24.1
RUN apk update && apk add --no-cache nginx=1.31.4
CMD ["nginx", "-g", "daemon off;"]
```

```bash
# CMD 지정 및 포트 바인딩 구동 테스트
docker build -t ch02-04-cmd-image .
docker run -d --name ch02-04-cmd-container -p 8080:80 ch02-04-cmd-image
curl http://localhost:8080
# 출력 결과: index.html 내용 확인
```

## 2.5 커스텀 웹 서버 이미지 단계별 빌드 및 검증 실습

- 지시어를 순차적으로 추가하여 Dockerfile을 완성하고, 각 단계마다 빌드 및 컨테이너 런타임 상태를 누적하여 검증함.

### 2.5.1 1단계: 베이스 이미지 선언 및 작업 디렉터리 설정 (`FROM`, `WORKDIR`)

- Alpine Linux 3.24.1 최신 베이스 이미지를 지정하고 작업 공간을 생성함.

```dockerfile
# 1단계 Dockerfile
FROM alpine:3.24.1
WORKDIR /app
```

- 빌드 및 검증 명령
  ```bash
  # 1단계 이미지 빌드
  docker build -t ch02-05-step1-image .

  # 컨테이너 구동 후 작업 디렉터리(/app) 생성 및 위치 확인
  docker run --rm ch02-05-step1-image pwd
  ```

### 2.5.2 2단계: 애플리케이션 파일 복사 (`COPY`)

- 호스트의 `index.html` 정적 웹 파일을 컨테이너 내부로 복사함.

```dockerfile
# 2단계 Dockerfile
FROM alpine:3.24.1
WORKDIR /app

# 정적 웹 파일 복사
COPY index.html .
```

- 빌드 및 검증 명령
  ```bash
  # 2단계 이미지 빌드
  docker build -t ch02-05-step2-image .

  # 컨테이너 내부 복사 파일 목록 확인
  docker run --rm ch02-05-step2-image ls -la /app
  ```

### 2.5.3 3단계: 환경 변수 선언 및 패키지 설치 (`RUN`, `ENV`, `ARG`)

- 빌드 임시 변수(`ARG`), 런타임 환경 변수(`ENV`), Nginx 웹 서버 패키지 설치(`RUN`)를 추가함.

```dockerfile
# 3단계 Dockerfile
FROM alpine:3.24.1
WORKDIR /app

ARG BUILD_VER=1.0.0
ENV APP_ENV=production

# Nginx 패키지 설치 및 정적 파일 위치 복사
RUN apk update && apk add --no-cache nginx=1.31.4
COPY index.html /usr/share/nginx/html/index.html
```

- 빌드 및 검증 명령
  ```bash
  # 빌드 인자를 전달하여 3단계 이미지 빌드
  docker build --build-arg BUILD_VER=1.0.0 -t ch02-05-step3-image .

  # 주입된 런타임 환경 변수 확인
  docker run --rm ch02-05-step3-image printenv APP_ENV
  ```

### 2.5.4 4단계: 수신 포트 명세 및 실행 명령어 지정 (`EXPOSE`, `CMD`)

- 포트 바인딩 명세(`EXPOSE`) 및 Nginx 데몬을 포그라운드로 유지하는 실행 명령(`CMD`)을 추가하여 완성함.

```dockerfile
# 4단계 최종 완성 Dockerfile
FROM alpine:3.24.1
WORKDIR /app

ARG BUILD_VER=1.0.0
ENV APP_ENV=production

RUN apk update && apk add --no-cache nginx=1.31.4
COPY index.html /usr/share/nginx/html/index.html

# 80번 포트 명세 및 Nginx 포그라운드 구동
EXPOSE 80
CMD ["nginx", "-g", "daemon off;"]
```

- 빌드 및 검증 명령
  ```bash
  # 최종 커스텀 이미지 빌드
  docker build -t ch02-05-final-image:1.0 .

  # 백그라운드로 8080 포트 바인딩 구동
  docker run -d --name ch02-05-final-container -p 8080:80 ch02-05-final-image:1.0

  # 웹 서버 수신 상태 검증
  curl http://localhost:8080
  ```

# 3. 애플리케이션 멀티 스테이지 빌드

- 멀티 스테이지 빌드 (Multi-stage Build): 빌드 타임 [^4] (JDK 포함) 종속성과 런타임 (JRE 전용) 환경을 별도 stage로 분리하여 최종 이미지 용량을 수백 MB 이상 경량화하는 빌드 기법.
    - 동작 원리: 하나의 Dockerfile 내부에서 여러 개의 FROM 절(Stage)을 정의하여 빌드 환경과 실행 환경을 독립적으로 구성함.
    - 빌드 단계 분리: 1단계(Build Stage)에서 JDK와 Gradle/Maven 등의 빌드 도구를 포함한 환경으로 소스코드를 컴파일하고 실행 가능한 아티팩트(JAR)를 생성함.
    - 런타임 결과물 추출: 2단계(Runtime Stage)에서는 최소한의 JRE 런타임 베이스 이미지를 선언한 후, `COPY --from=builder` 구문을 통해 1단계에서 생성된 아티팩트만 선택적으로 가져옴.
    - 용량 및 보안 개선: 1단계에 존재하던 소스코드, 컴파일러, 임시 빌드 캐시 등의 부산물은 최종 이미지에 포함되지 않고 완전히 제거되므로 경량화와 보안성 향상을 동시에 달성함.

```dockerfile
# Stage 1: Build stage (JDK 25 환경에서 소스 코드 빌드)
FROM eclipse-temurin:25-jdk-alpine AS builder
WORKDIR /app

# Gradle 래퍼 및 빌드 설정 파일 선 복사 (레이어 캐싱 활용)
COPY gradlew .
COPY gradle gradle
COPY build.gradle .
COPY settings.gradle .

# 실행 권한 부여 및 의존성 다운로드
RUN chmod +x ./gradlew
RUN ./gradlew dependencies --no-daemon

# 소스 코드 복사 및 실행 가능한 JAR 파일 생성
COPY src src
RUN ./gradlew bootJar --no-daemon

# Stage 2: Runtime stage (경량화된 JRE 25 런타임 환경 구성)
FROM eclipse-temurin:25-jre-alpine
WORKDIR /app

# 보안 강화를 위한 비루트(non-root) 전용 시스템 계정 생성
RUN addgroup -S appgroup && adduser -S appuser -G appgroup

# Stage 1에서 빌드된 최종 jar 파일만 추출하여 복사
COPY --from=builder /app/build/libs/*.jar app.jar

# 소유권 변경 및 계정 전환
RUN chown -R appuser:appgroup /app
USER appuser

EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]
```

# 4. .dockerignore 및 레이어 캐시 최적화 기법

## 4.1 .dockerignore 파일 작성

- .dockerignore
    - Docker 빌드 컨텍스트(Build Context)를 구성할 때 이미지 내부로 복사할 필요가 없는 불필요한 파일이나 보안 민감 문서 등을 지정하여 빌드 속도 및 보안성을 향상시키는 설정 파일.
- 작성 모범 사례
    - Git 버전 관리 디렉터리(`.git`), 빌드 산출물(`target/`, `build/`), 환경 설정 파일(`.env`) 등을 선제적으로 제외 처리함.

```dockerignore
.git
.gitignore
build/
target/
*.md
.env
```

## 4.2 레이어 캐시 (Layer Cache) 활용 원칙

- 캐시 적중 조건 및 부모 레이어 종속성
    - 도커 캐시는 지시어 개별 단위가 아니라 1단계(`FROM`)부터 해당 지시어까지의 부모 레이어 체인이 완벽히 일치할 때만 적중(Cache Hit)됨.
    - 상단 지시어에서 내용이나 파일 수정으로 캐시 미스(Cache Miss)가 일어날 경우, 그 하위에 위치한 모든 지시어의 캐시가 일괄 무효화(Invalidation)됨.
- 지시어 배치 순서 최적화 원칙
    - 변경 빈도가 낮은 레이어(베이스 이미지 선언, OS 패키지 설치, 의존성 라이브러리 다운로드 등)를 Dockerfile 상단에 우선 배치함.
    - 변경 빈도가 높은 레이어(소스코드 복사, 컴파일 빌드 실행, 런타임 구동 명령 등)를 Dockerfile 하단에 배치하여 하위 레이어 무효화 파급을 최소화함.

## 각주
[^1]: 베이스 (Base) 이미지: 새로운 Docker 이미지를 구축할 때 바탕이 되는 출발점 이미지.
[^2]: 스냅샷 (Snapshot): 특정 시점의 파일 시스템 전체 상태 및 데이터를 있는 그대로 저장한 읽기 전용 복사본.
[^3]: 유니온 파일시스템 (Union File System): 여러 개의 파일 시스템 레이어를 하나로 겹쳐서 단일 통합 파일 시스템 디렉터리로 보여주는 가상화 파일 시스템 기술.
[^4]: 빌드 타임 (Build Time): 소스 코드를 컴파일하고 실행 가능한 바이너리나 패키지로 변환하는 프로세스 단계.
[^5]: 빌드 컨텍스트 (Build Context): `docker build` 명령 실행 시 Client가 Daemon으로 전달하는 작업 디렉토리의 파일 및 폴더 전체 모음.
[^6]: 레이어 캐시 (Layer Cache): 이전에 빌드한 Dockerfile 지시어의 실행 결과 레이어를 재사용하여 빌드 시간을 단축하는 기능.
