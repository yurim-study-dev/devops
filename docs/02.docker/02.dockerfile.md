# 1. Dockerfile 개요

## 1.1 Dockerfile 도입 배경

### 1.1.1 Dockerfile
- Dockerfile은 애플리케이션을 컨테이너화하는 데 필요한 베이스 이미지 [^1] 지정, 런타임 종속성 설치, 소스코드 파일 복사, 환경 변수 선언, 구동 명령 등을 텍스트 형식으로 명시한 자동화 빌드 명세서.
- `docker build` 명령어를 수행하면 도커 데몬(Docker Daemon)이 Dockerfile에 정의된 명령 지시어를 위에서 아래로 순차 해석하여 컨테이너 이미지를 생성함.
- Dockerfile 예시
  ```dockerfile
  # 1. 베이스 이미지 지정 (Alpine Linux 3.24.1)
  FROM alpine:3.24.1

  # 2. 컨테이너 내부 작업 디렉터리 설정
  WORKDIR /app

  # 3. 런타임 환경 변수 선언
  ENV APP_ENV=production

  # 4. 웹 서버(Nginx) 패키지 설치 및 파일 복사(https://pkgs.alpinelinux.org/packages 에서 패키지 버전 확인)
  RUN apk update && apk add --no-cache nginx=1.30.4-r1
  COPY default.conf /etc/nginx/http.d/default.conf
  COPY index.html /usr/share/nginx/html/index.html

  # 5. 수신 포트 명세 및 포그라운드 구동 명령 지정
  EXPOSE 80
  CMD ["nginx", "-g", "daemon off;"]
  ```

### 1.1.2 인프라 구축 방식의 패러다임 전환
- 전통적 수동 구축 방식: 시스템 관리자가 서버 OS에 직접 접속하여 쉘 스크립트 실행이나 패키지 명령을 수동으로 실행함. 이로 인해 작업자 간 설정 오차, 환경 문서화 누락, 런타임 버전 파편화 및 불일치 문제가 발생함.
- Dockerfile 기반 자동화 방식: 인프라 구성을 코드로 명시하는 코드로서의 인프라(IaC, Infrastructure as Code) 패러다임을 실현함. 인프라 명세 자체가 버전 관리 시스템(Git)에 의해 관리되므로 환경 구축 과정이 동일하게 재현됨.

## 1.2 Dockerfile 핵심 구성 요소 및 레이어 메커니즘

### 1.2.1 Dockerfile 지시어 (Instructions)
- Dockerfile 내에서 이미지를 생성하기 위한 동작을 도커 데몬에 전달하는 대문자 텍스트 명령 키워드.
- 베이스 이미지 지정(`FROM`), 패키지 설치 및 명령어 실행(`RUN`), 파일 복사(`COPY`), 런타임 환경 변수 선언(`ENV`), 컨테이너 구동 시 기본 실행 명령(`CMD`) 등으로 구성됨.
- 작성된 각 지시어는 이미지 빌드 시 하나의 독립된 층(Layer)을 형성하는 기본 단위로 작동함.

### 1.2.2 이미지 레이어 (Image Layer)
- 도커 이미지는 단일 통째 파일이 아니라, 여러 개의 읽기 전용(Read-Only) 파일시스템 스냅샷 [^2] 인 레이어가 차곡차곡 쌓여 완성되는 유니온 파일시스템 [^3] (Union File System) 구조.
- Dockerfile에서 런타임 환경을 변경하는 주요 지시어(`FROM`, `RUN`, `COPY`, `ADD` 등)가 실행될 때마다 이전 레이어 위에 새로운 읽기 전용 레이어가 커밋되어 중첩 저장됨.
- 동일한 베이스 이미지나 라이브러리 레이어는 여러 다른 이미지 간에 물리적으로 공유되므로 디스크 공간을 절약하고 다운로드 속도를 향상시킴.

### 1.2.3 부모 레이어 체인과 캐시 무효화 원리
- 각 레이어는 독립적으로 분리되어 임의 재사용되는 것이 아니라, 1단계(`FROM`)부터 상위 단계까지 부모 레이어의 해시 체인으로 결합된 순차적 누적 구조.
- 1단계부터 현재 단계까지 부모 레이어와 지시어 내용(명령어 구문 및 파일 해시 등)이 완전히 일치할 때만 캐시(`Using cache`)가 재활용됨.
- 중간 단계에서 변경이 발생하여 캐시 미스(Cache Miss)가 일어나면, 해당 단계를 포함하여 이후의 모든 하위 레이어 캐시는 전면 무효화(Cache Invalidation)되어 새로 실행 및 커밋됨.

### 1.2.4 컨테이너 레이어와 Copy-on-Write (CoW) 원리
- 이미지 전체 파일시스템의 컨테이너 내부 복사 배제
  - 컨테이너가 구동(`docker run`)될 때 이미지 데이터 전체가 물리적으로 복사되는 것이 아니라, 하위의 읽기 전용 이미지 레이어들을 그대로 공유 참조(Union Mount)하는 구조.
  - 컨테이너 구동 시점에는 최상단에 수 KB 크기의 얇은 읽고 쓰기 가능 컨테이너 레이어(Writable Layer)만 새로 추가됨.
- 파일 수정 시의 Copy-on-Write (CoW) 동작
  - 컨테이너 내부에서 기존 읽기 전용 레이어에 존재하는 파일을 수정할 경우, 도커는 해당 파일만 최상단 컨테이너 레이어로 복사하여 수정하는 Copy-on-Write 방식을 적용함.
  - 이에 따라 하위 이미지 레이어의 원본 파일은 변경되지 않고 유지되며, 컨테이너가 파기되더라도 원본 이미지 레이어는 안전하게 보존됨.

## 1.3 전통적 배포 방식과 Dockerfile 기반 방식의 비교

### 1.3.1 환경 명세의 표준화 및 격리성
- 전통적 배포 환경에서는 호스트 OS에 종속된 라이브러리 및 환경 변수 충돌로 인해 다중 애플리케이션 공존이 제한적임.
- Dockerfile을 통한 빌드 방식은 독립된 파일시스템과 실행 격리 환경을 보장하는 이식성 높은 전용 이미지를 생성함.

### 1.3.2 협업 체계 및 검증 효율성
- 개발, 검증(QA), 스테이징, 운영 환경 전반에 걸쳐 유효성이 검증된 인프라 템플릿(Dockerfile) 하나로 동일한 이미지 생성을 보장함.
- 새로운 개발 인원이 팀에 합류하더라도 단일 `docker build` 실행만으로 복잡한 개발 환경 세팅을 수 초 내에 자동 완성함.

## 1.4 Dockerfile 빌드 파이프라인 동작 원리

### 1.4.1 빌드 컨텍스트 (Build Context) 전송
- 도커 클라이언트와 데몬 간 작업 디렉터리 압축 전송
  - 사용자가 `docker build` 명령을 입력하면 도커 클라이언트는 지정된 작업 디렉터리 내부의 모든 파일과 하위 폴더를 압축하여 도커 데몬 서비스로 전송함.
  - 도커 데몬은 전달받은 압축 파일을 바탕으로 이미지를 빌드하며, 이 전송 데이터 영역을 빌드 컨텍스트 [^5] (Build Context)라 부름.
- 파일 접근 허용 경계선 역할 및 제외 처리
  - Dockerfile 내의 `COPY` 및 `ADD` 지시어는 오직 빌드 컨텍스트에 포함되어 전달된 파일만 이미지로 복사할 수 있으며, 이 영역 바깥의 호스트 파일에는 접근할 수 없음.
  - 작업 디렉터리 내에 불필요한 대용량 파일이 포함되어 빌드가 지연되는 것을 방지하기 위해 `.dockerignore` 파일을 활용하여 전송 대상에서 선제적으로 제외함.
  - `.dockerignore` 파일 예시
    ```gitignore
    # 1. 모든 파일/폴더를 전송 대상에서 제외
    *
    # 2. 오직 JAR 결과물과 Dockerfile만 예외로 전송 대상에 포함
    !build/libs/*.jar
    !Dockerfile
    ```
- 최신 BuildKit 빌드 엔진의 지능형 전송 (Lazy Transfer) 메커니즘
  - 최신 BuildKit 엔진은 Dockerfile 구문을 미리 분석하여 `COPY` 등에 지정된 대상 파일의 해시(Checksum)만 지능적으로 추적 및 최소 전송하므로, 지정되지 않은 주변 파일이 변경되어도 캐시가 유지됨.
  - 다만, `COPY . .` 구문 사용 시의 캐시 파기 방지, 초기 파일 상태(Stat) 스캔 지연 차단, 민감 정보 유출 방지를 위해 `.dockerignore` 작성은 여전히 필수적인 모범 사례로 다뤄짐.

### 1.4.2 지시어 해석 및 캐싱 기반 레이어 커밋
- 임시 컨테이너 구동을 통한 명령 실행 및 레이어 커밋
  - 도커 이미지는 읽기 전용(Read-Only)이므로 이미 형성된 레이어 내부에서는 리눅스 명령(`RUN` 등)을 직접 실행하거나 파일을 직접 수정할 수 없음.
  - 이에 따라 도커 데몬은 이전 레이어 위에 쓰기 가능한 임시 컨테이너를 구동하고, 그 격리된 작업 공간 안에서 해당 지시어 명령을 실행함.
  - 명령 실행이 완료되면 변경된 파일시스템 상태만 새로운 읽기 전용 레이어로 스냅샷 [^2] 커밋(`docker commit`)한 뒤 사용된 임시 컨테이너를 즉시 파기함.
- 캐시 적중을 통한 빌드 재활용
  - 이전 빌드 이력과 비교하여 상단 지시어 구문 및 파일 내용이 동일한 경우, 도커 데몬은 이전 빌드에서 생성된 레이어 캐시 [^6] 를 자동으로 재활용(`Using cache`)하여 해당 단계의 명령 실행을 스킵함.

| [RUN](https://docs.docker.com/reference/dockerfile/#run) | 이미지 빌드 중 리눅스 셸 명령어 실행 및 새로운 레이어 생성. |
| [SHELL](https://docs.docker.com/reference/dockerfile/#shell) | 명령어 실행 시 사용할 기본 셸 프로그램 지정. |
| [STOPSIGNAL](https://docs.docker.com/reference/dockerfile/#stopsignal) | 컨테이너 종료 시 전달할 시스템 콜 시그널 지정. |
| [USER](https://docs.docker.com/reference/dockerfile/#user) | 명령어 실행 및 컨테이너 구동 시 적용할 사용자/그룹 계정 설정. |
| [VOLUME](https://docs.docker.com/reference/dockerfile/#volume) | 데이터 지속성 확보를 위한 볼륨 마운트 포인트 선언. |
| [WORKDIR](https://docs.docker.com/reference/dockerfile/#workdir) | 컨테이너 내부의 작업 기준 디렉터리 설정 및 이동. |

## 2.1 기반 환경 설정 (`FROM`, `LABEL`, `WORKDIR`)

### 2.1.1 베이스 이미지 선언 (`FROM`)

- 개념 및 특징
  - 이미지 빌드 시 기준이 되는 베이스 이미지를 지정함.
  - Dockerfile 내에서 가장 먼저 선언되어야 하며, 특정 버전을 의미하는 태그(예: `alpine:3.24.1`, `eclipse-temurin:25-jdk-alpine`)를 명시하여 빌드 환경의 재현성을 보장함.
- 가변 태그(Mutable Tag) 사용 시 주의사항
  - 가변 태그 위험성: `FROM nginx:1.31`나 `FROM alpine:latest`와 같이 버전 범위가 넓은 태그를 사용할 경우, 원격 레지스트리의 최신 이미지 갱신 상태에 따라 빌드 시점마다 서로 다른 베이스 이미지 레이어가 다운로드될 위험이 존재함.
  - 환경 불일치 발생 원인: 로컬 개발 환경에서는 이전에 다운로드되어 캐시된 베이스 이미지(예: `1.31.3` 기준)를 계속 재활용하는 반면, 캐시가 비어있는 운영 서버에서는 원격 레지스트리의 최신 베이스 이미지(예: `1.31.4` 기준)를 새로 다운로드받게 됨.
  - 장애 파급 효과: 이로 인해 개발 환경에서는 정상 작동하던 애플리케이션이 운영 배포 시점에 버전 차이로 인한 런타임 오류를 일으키는 개발-운영 환경 불일치 문제가 초래됨.
  - 명세 모범 사례: 실무에서는 패치 버전까지 명확히 고정된 태그(`FROM nginx:1.31.4`)를 사용하거나, 이미지 고유 해시값(`FROM nginx@sha256:a1b2c3...`)을 선언하여 모든 환경에서 100% 동일한 베이스 이미지 사용을 보장함.

```dockerfile

```

- 💻 실습: [ch02-01/commands.sh](../../workspace/02_docker/dockerfile/ch02-01/commands.sh)
```bash

# 전체 LABEL 메타데이터 정보 확인 (JSON 포맷 출력)

# 출력 결과: {"description":"Spring Board Nginx Web Server Image","environment":"production","maintainer":"kilyong <kilyong@example.com>","version":"1.0.0"}

# 특정 LABEL key 값 단독 추출 확인 (점 표기법 방식)
docker inspect --format='{{.Config.Labels.version}}' ch02-01-label-image
# 출력 결과: 1.0.0

# 특정 LABEL key 값 단독 추출 확인 (index 함수 방식)
docker inspect --format='{{index .Config.Labels "environment"}}' ch02-01-label-image
# 출력 결과: production

# 특정 LABEL Key=Value 완전 일치 기반 이미지 필터링 검색

# 특정 LABEL Key 유무 기반 컨테이너 필터링 검색 (Key 이름만 지정)

# 특정 LABEL Key=Value 완전 일치 기반 컨테이너 필터링 검색
docker ps -a --filter "label=environment=production"
```

- 이미지 및 컨테이너 상세 정보 추출 문법 (Go Template)
  - 전체 JSON 변환 (`{{json .Config.Labels}}`): 지정한 객체(라벨, 네트워크, 볼륨 등)의 전체 구조 데이터를 가독성 높은 표준 JSON 포맷으로 변환하여 출력함.
  - 단일 속성 점 표기법 (`{{.Config.Labels.version}}`): 특수문자가 없는 단순 영문 속성 키 이름일 경우 점(.) 표기법을 통해 직관적이고 간결하게 단독 추출함.
  - 단일 속성 index 함수 (`{{index .Config.Labels "key"}}`): 속성 키 이름에 점(.)이나 하이픈(-) 등의 특수문자가 포함되어 점 표기법 사용 시 구문 오류가 발생하는 경우 `index` 내장 함수를 사용하여 안전하게 단독 추출함.

## 2.2 파일 복사 (`ADD`, `COPY`)

### 2.2.1 원격 파일 다운로드 및 압축 해제 (`ADD`)
- 호스트 파일 복사 기능뿐만 아니라 원격 URL 파일 다운로드 및 tar 아카이브 자동 압축 해제 기능을 제공함.
- 호스트 로컬의 tar 계열 압축 파일(`.tar`, `.tar.gz`, `.tgz` 등)을 복사할 때만 컨테이너 내부로 자동 압축 해제(Unpack)되며, `.zip` 파일이나 원격 URL로 다운로드받은 파일은 자동 해제되지 않고 파일 그대로 복사됨.
- 의도치 않은 압축 해제 부작용 주의
  - tar 압축 파일 원본 자체를 보관하고 싶은 경우에도 `ADD`는 무조건 압축을 풀어버려 파일 시스템을 어지럽히는 부작용이 발생함.
  - 단순 파일 복사 시에는 `COPY` 지시어를 사용하는 것이 권장됨.

### 2.2.2 소스코드 및 파일 복사 (`COPY`)
- 호스트 시스템의 파일이나 디렉터리를 컨테이너 내부의 지정한 경로로 단순 복사.
- 다중 파일 복사 및 문법 패턴
  - 단일 COPY 지시어에서 다중 복사: `COPY index.html hello.html /app/` 형태로 여러 대상 파일을 나열하여 단일 레이어로 복사함.
  - 와일드카드 사용: `COPY *.html /app/`과 같이 특정 확장자나 패턴의 파일 모음을 일괄 복사함.
  - 다중 COPY 지시어 나열: `COPY` 지시어를 여러 줄로 나누어 단계별로 나열함. 자주 변경되지 않는 설정 파일(예: `build.gradle`, `package.json`)을 먼저 복사한 후 소스코드를 복사하면 도커 레이어 캐시 활용도를 높일 수 있음.

## 2.3 환경 설정 및 빌드 (`ARG`, `ENV`, `RUN`)

### 2.3.1 빌드 임시 변수 지정 (`ARG`)
- Dockerfile 내부의 빌드 시점 전용 변수로 선언하여 활용함.
- 빌드 과정에서만 일회성으로 사용되며, 최종 런타임 컨테이너 환경 변수에는 유지되지 않고 소멸함.
- 이미지 빌드 시 `docker build --build-arg APP_VERSION=2.0.0` 형태로 인자를 전달하면 기본값이 덮어써지고(오버라이드), 인자를 넘기지 않으면 선언된 기본값이 그대로 사용됨.

- 💻 실습: [ch02-03/arg/Dockerfile](../../workspace/02_docker/dockerfile/ch02-03/arg/Dockerfile)
```dockerfile
# 베이스 이미지 지정
FROM eclipse-temurin:25-jre

# 빌드 시점 임시 변수 선언 (기본값: 1.0.0)
ARG APP_VERSION=1.0.0

# 주입받은 빌드 변수를 이미지 메타데이터(LABEL)로 등록
LABEL APP_VER=$APP_VERSION
LABEL APP_DESCRIPTION="Hello World App version: $APP_VERSION"
```

- 💻 실습: [ch02-03/arg/commands.sh](../../workspace/02_docker/dockerfile/ch02-03/arg/commands.sh)
```bash
# --build-arg 옵션으로 빌드 변수(APP_VERSION=2.0.0)를 전달하여 이미지 빌드
docker build --build-arg APP_VERSION=2.0.0 -t ch02-03-arg-image .

# 기존 컨테이너 삭제 후 새 컨테이너 구동
docker rm -f ch02-03-arg-container
docker run -d --name ch02-03-arg-container ch02-03-arg-image

# 주입된 빌드 변수가 LABEL 메타데이터에 전달된 결과 확인
docker inspect ch02-03-arg-container
```

### 2.3.2 런타임 환경 변수 선언 (`ENV`)
- 컨테이너 내부 런타임 환경 변수를 키-값(`KEY=VALUE`) 쌍으로 선언함.
- 지정된 환경 변수는 이미지 빌드 과정뿐만 아니라 구동 중인 컨테이너 내부 프로세스에도 지속 유지됨.
- Dockerfile에 기본값을 지정해두더라도 컨테이너 구동(`docker run -e`) 시점에 유연하게 오버라이드하여 주입할 수 있음.

- 💻 실습: [ch02-03/env/Dockerfile](../../workspace/02_docker/dockerfile/ch02-03/env/Dockerfile)
```dockerfile
# 베이스 이미지 지정
FROM eclipse-temurin:25-jre

# 빌드 시점 임시 변수 선언 (기본값: 1.0.0)
ARG APP_VERSION=1.0.0

# 이미지 메타데이터(LABEL) 명세
LABEL APP_VER=$APP_VERSION
LABEL APP_DESCRIPTION="Hello World App version: $APP_VERSION"

# 런타임 환경 변수 기본값 선언 (PORT=80)
ENV PORT=80
```

- 💻 실습: [ch02-03/env/commands.sh](../../workspace/02_docker/dockerfile/ch02-03/env/commands.sh)
```bash
# 이미지 빌드
docker build --build-arg APP_VERSION=3.0.0 -t ch02-03-env-image .

# 기존 컨테이너 삭제 및 기본 ENV 환경 변수(PORT=80)로 구동
docker rm -f ch02-03-env-container
docker run -d --name ch02-03-env-container ch02-03-env-image tail -f //dev/null

# 컨테이너 쉘 접속
docker exec -it ch02-03-env-container //bin/sh

# 컨테이너 내부 쉘에서 환경 변수 확인
printenv PORT
# 출력 결과: 80

# 기존 컨테이너 삭제 및 -e 옵션으로 런타임 환경 변수(PORT=8080) 오버라이드 구동
docker rm -f ch02-03-env-container
docker run -d -e PORT=8080 --name ch02-03-env-container ch02-03-env-image tail -f //dev/null

# 컨테이너 쉘 접속
docker exec -it ch02-03-env-container //bin/sh

# 컨테이너 내부 쉘에서 환경 변수 오버라이드 결과 확인
printenv PORT
# 출력 결과: 8080
```

### 2.3.3 이미지 빌드 명령 실행 (`RUN`)

## 2.4 런타임 명세 (`EXPOSE`, `CMD`, `ENTRYPOINT`)

### 2.4.2 런타임 기본 명령어 지정 (`CMD`)
- 컨테이너 구동(`docker run`) 후 실행할 기본 명령어를 설정.
- `docker run` 실행 시 뒤에 인자를 전달하면 기존 `CMD` 명령어 전체가 덮어씌워짐(Override).

- 💻 실습: [ch02-04/cmd/Dockerfile](../../workspace/02_docker/dockerfile/ch02-04/cmd/Dockerfile)
```dockerfile
# 베이스 이미지 지정 및 CMD 기본 명령어 설정
FROM alpine:3.24.1
CMD ["echo", "hello"]
```

- 💻 실습: [ch02-04/cmd/commands.sh](../../workspace/02_docker/dockerfile/ch02-04/cmd/commands.sh)
```bash
docker build -t ch02-04-cmd-image .

# 인자 없이 기본 구동 (CMD 기본 명령어 실행: echo hello)
docker run --rm ch02-04-cmd-image
# 출력 결과: hello

# 인자를 주어 구동 (기존 CMD가 덮어씌워지고 echo world 실행)
docker run --rm ch02-04-cmd-image echo world
# 출력 결과: world
```

### 2.4.3 런타임 고정 명령어 지정 (`ENTRYPOINT`)
- 컨테이너 구동 후 항상 고정하여 실행할 명령어를 설정.
- `docker run` 실행 시 전달된 인자는 `ENTRYPOINT` 명령어를 덮어쓰지 않고 명령행 매개변수(Argument)로 추가 전달됨.

- 💻 실습: [ch02-04/entrypoint/HelloWorld.java](../../workspace/02_docker/dockerfile/ch02-04/entrypoint/HelloWorld.java)
```java
static void main(String[] args){
    System.out.println("Hello " + String.join(" ", args));
}
```

- 💻 실습: [ch02-04/entrypoint/Dockerfile](../../workspace/02_docker/dockerfile/ch02-04/entrypoint/Dockerfile)
```dockerfile
# 1. JDK 베이스 이미지 지정 및 작업 디렉터리 생성
FROM eclipse-temurin:25-jdk-alpine
WORKDIR /app

# 2. 자바 소스코드 파일 복사
COPY *.java .

# 3. RUN 지시어로 자바 소스코드 직접 컴파일 및 소스 파일 제거
RUN javac *.java
RUN rm *.java

# 4. 런타임에 항상 고정으로 실행할 메인 명령어 지정
ENTRYPOINT ["java", "HelloWorld", "Java"]
```

- 💻 실습: [ch02-04/entrypoint/commands.sh](../../workspace/02_docker/dockerfile/ch02-04/entrypoint/commands.sh)
```bash
# 이미지 빌드
docker build -t ch02-04-entrypoint-image .

# 인자 없이 기본 구동 (ENTRYPOINT 기본 인자 전달)
docker run --rm ch02-04-entrypoint-image
# 출력 결과: Hello Java

# 추가 인자("World")를 전달하여 구동 (ENTRYPOINT 뒤에 매개변수로 결합됨)
docker run --rm ch02-04-entrypoint-image World
# 출력 결과: Hello Java World
```

- `RUN`, `CMD`, `ENTRYPOINT` 지시어의 비교

| 지시어 | 실행 시점 | 인자 덮어쓰기(Override) 여부 | 주요 용도 |
| --- | --- | --- | --- |
| `RUN` | 빌드 시점 (`docker build`) | 불가능 (이미지 생성 시점에만 1회 실행) | 패키지 설치, 파일 삭제, 소스 컴파일 등 레이어 생성 |
| `CMD` | 런타임 시점 (`docker run`) | 가능 (`docker run` 뒤 인자로 전체 덮어써짐) | 컨테이너 구동 시 기본 실행 명령어 및 기본 매개변수 |
| `ENTRYPOINT` | 런타임 시점 (`docker run`) | 불가 (`docker run` 뒤 인자가 매개변수로 수신됨) | 컨테이너 구동 시 고정으로 실행할 메인 프로세스 지정 |

### 2.4.4 `ENTRYPOINT`와 `CMD` 결합 활용
- `ENTRYPOINT`에 메인 실행 명령을 고정하고, `CMD`에 기본 매개변수(Default Argument)를 지정하면 `CMD`에 작성된 값은 명령어로 인식하지 않고 `ENTRYPOINT` 뒤에 자동으로 결합되어 매개변수로 사용됨.
- 컨테이너 구동 시 인자를 지정하지 않으면 `CMD`에 선언된 기본 매개변수로 구동되며, 인자를 지정하면 `CMD` 파라미터만 유연하게 오버라이드됨.

- 💻 실습: [ch02-04/entrypoint/Dockerfile](../../workspace/02_docker/dockerfile/ch02-04/entrypoint/Dockerfile)
```dockerfile
# ENTRYPOINT 및 CMD 결합 사용 예시
FROM alpine:3.24.1

# 1. 고정 실행 명령어 지정 (echo)
ENTRYPOINT ["echo", "hello"]

# 2. 기본 매개변수 지정 (ENTRYPOINT 인자로 결합되어 전달됨)
CMD ["world"]
```

- 💻 실습: [ch02-04/entrypoint/commands.sh](../../workspace/02_docker/dockerfile/ch02-04/entrypoint/commands.sh)
```bash
# 1. 인자 없이 기본 구동 (CMD 매개변수 적용: echo hello world)
docker run --rm ch02-04-cmd-image
# 출력 결과: hello world

# 2. 인자 전달 구동 (CMD 매개변수 오버라이드: echo hello docker)
docker run --rm ch02-04-cmd-image docker
# 출력 결과: hello docker
```

  - `SERVER_PORT`: 도커 `ENV`로 주입한 환경 변수가 스프링 부트의 `server.port` 속성으로 자동 매핑되어 내장 톰캣 수신 포트 번호를 지정.

# 3. 애플리케이션 멀티 스테이지 빌드

- 멀티 스테이지 빌드 (Multi-stage Build): 빌드 타임 [^4] (JDK 포함) 종속성과 런타임 (JRE 전용) 환경을 별도 stage로 분리하여 최종 이미지 용량을 경량화하는 빌드 기법.
  - 동작 원리: 하나의 Dockerfile 내부에서 여러 개의 FROM 절(Stage)을 정의하여 빌드 환경과 실행 환경을 독립적으로 구성함.
  - 빌드 단계 분리: 1단계(Build Stage)에서 JDK와 Gradle/Maven 등의 빌드 도구를 포함한 환경으로 소스코드를 컴파일하고 실행 가능한 아티팩트(JAR)를 생성함.
  - 런타임 결과물 추출: 2단계(Runtime Stage)에서는 최소한의 JRE 런타임 베이스 이미지를 선언한 후, `COPY --from=builder` 구문을 통해 1단계에서 생성된 아티팩트만 선택적으로 가져옴.
  - 용량 및 보안 개선: 1단계에 존재하던 소스코드, 컴파일러, 임시 빌드 캐시 등의 부산물은 최종 이미지에 포함되지 않고 완전히 제거되므로 경량화와 보안성 향상을 동시에 달성함.
- 컨테이너 내부에서 프로젝트 빌드를 수행하는 이유
  - 호스트 환경 독립성 확보: 개발자의 로컬 PC나 CI/CD 서버에 JDK 및 Gradle 등의 빌드 도구가 설치되어 있지 않거나 버전이 달라도, 도커 데몬만 있으면 어디서나 명시된 동일한 빌드 환경을 보장함.
  - 파이프라인 일관성 및 이식성: 호스트 환경 파편화에 따른 빌드 실패를 차단하고, 개발·검증·운영 전체 빌드 절차를 일관되게 표준화함.
  - 빌드 환경 격리 및 보안: 소스코드와 컴파일 도구를 최종 런타임 이미지에 남기지 않고 빌드 전용 스테이지에서만 격리하여 소비하고 파기함.
- 이전의 단일 스테이지 방식(`Dockerfile.simple`)은 호스트 환경에서 수동 빌드(`./gradlew bootJar`) 후 아티팩트(JAR)만 복사하는 구조였으나, 멀티 스테이지 방식은 이 빌드 과정 자체를 컨테이너 내부로 완전 자동화함.

> [!NOTE]
> - 실행할 모든 명령은 spring-board 프로젝트 docs 폴더 아래의 `docker-file-multi-stage.sh` 파일에 저장한 후 IntelliJ의 spring-board 프로젝트 터미널에서 실행.
> - 기존 `Dockerfile`은 [Dockerfile.single.stage](https://github.com/BEBC-25/project-board/blob/main/Dockerfile.single.stage)로 파일명을 변경하여 백업하고 새로운 `Dockerfile`을 생성해서 진행.

- 💻 실습: [Dockerfile](https://github.com/BEBC-25/project-board/blob/main/Dockerfile)

# Gradle 래퍼 및 빌드 설정 파일 복사 (레이어 캐싱 활용)

COPY gradle/ gradle/
COPY build.gradle .
COPY settings.gradle .

# 실행 권한 부여 및 의존성 라이브러리 사전 다운로드
# (소스코드 변경 시 매번 무거운 라이브러리를 다시 다운로드받는 것을 방지하여 레이어 캐시 활용을 높임)

# 4. .dockerignore 및 레이어 캐시 최적화 기법

## 4.1 .dockerignore 파일 작성

- .dockerignore
  - Docker 빌드 컨텍스트(Build Context)를 구성할 때 이미지 내부로 복사할 필요가 없는 불필요한 파일이나 보안 민감 문서 등을 지정하여 빌드 속도 및 보안성을 향상시키는 설정 파일.
- 작성 모범 사례
  - 컨테이너 이미지 빌드에 불필요한 Git 버전 관리 디렉터리(`.git`), 빌드 산출물(`target/`, `build/`), 환경 설정 파일(`.env`) 등을 미리 제외 처리함.

```dockerignore
.git
.gitignore
build/
target/
*.md
.env
```

## 4.2 레이어 캐시 (Layer Cache) 활용 원칙

- 도커 레이어 캐시의 동작 메커니즘
  - 도커 데몬은 이미지 빌드 시 `FROM` 절부터 각 지시어(Instruction)가 생성하는 레이어의 해시값과 기존 캐시 레이어를 1대1로 검증함.
  - 상단 지시어 구문 및 파일 내용이 이전 빌드와 완전히 동일할 경우 `Using cache` 메시지와 함께 캐시를 재활용하여 중복 실행을 스킵함.
- 지시어별 캐시 변경 감지(Invalidation) 검사 원리
  - `RUN`, `ENV`, `WORKDIR` 지시어: 지시어의 텍스트 명령어 구문 자체가 변경되었는지만 검사함.
  - `COPY`, `ADD` 지시어: 명령어 구문뿐만 아니라 복사하려는 호스트 파일의 내용(체크섬/Checksum 해시값)을 직접 검사함. 소스코드 파일의 단 1줄이라도 변경되면 캐시 미스(Cache Miss)가 발생함.
- 연쇄적 캐시 무효화 (Cascade Invalidation) 현상
  - 특정 상단 레이어에서 캐시 미스가 발생하면, 그 지시어를 포함하여 그 하위에 위치한 모든 지시어의 캐시가 자동으로 연쇄 무효화(Invalidated)되어 다시 재실행됨.
- 지시어 배치 최적화 패턴 비교
  - 비효율적 배치 패턴 (Bad Case): 소스코드(`COPY src src`)를 먼저 복사한 후 의존성 라이브러리 다운로드(`RUN ./gradlew dependencies`)를 수행하는 구조. 소스코드가 수정될 때마다 무거운 의존성 다운로드 지시어의 캐시가 무효화되어 매번 수 분 이상 빌드 시간이 소요됨.
  - 최적화 배치 패턴 (Good Case): 자주 바뀌지 않는 의존성 설정 파일(`build.gradle`, `package.json`)만 상단에서 먼저 복사하고 의존성을 다운로드한 후, 자주 변경되는 애플리케이션 소스코드(`COPY src src`)를 하단에 배치함. 소스코드가 수정되어도 라이브러리 다운로드 레이어 캐시는 100% 재활용되므로 빌드 시간을 초 단위로 단축함.

```dockerfile
# 최적화된 Dockerfile 지시어 배치 예시 (Java Gradle 기준)
FROM eclipse-temurin:25-jdk-alpine AS builder
WORKDIR /app

# 1. 변경 빈도가 낮은 Gradle 설정 파일만 먼저 복사 및 의존성 다운로드 (캐시 활용 극대화)
COPY gradlew .
COPY gradle gradle
COPY build.gradle .
COPY settings.gradle .
RUN chmod +x ./gradlew
RUN ./gradlew dependencies --no-daemon

# 2. 자주 변경되는 애플리케이션 소스코드는 의존성 다운로드 이후 하단에 배치
COPY src src
RUN ./gradlew bootJar --no-daemon
```

## 각주
[^1]: 베이스 (Base) 이미지: 새로운 Docker 이미지를 구축할 때 바탕이 되는 출발점 이미지.
[^2]: 스냅샷 (Snapshot): 특정 시점의 파일 시스템 전체 상태 및 데이터를 있는 그대로 저장한 읽기 전용 복사본.
[^3]: 유니온 파일시스템 (Union File System): 여러 개의 파일 시스템 레이어를 하나로 겹쳐서 단일 통합 파일 시스템 디렉터리로 보여주는 가상화 파일 시스템 기술.
[^4]: 빌드 타임 (Build Time): 소스 코드를 컴파일하고 실행 가능한 바이너리나 패키지로 변환하는 프로세스 단계.
[^5]: 빌드 컨텍스트 (Build Context): `docker build` 명령 실행 시 Client가 Daemon으로 전달하는 작업 디렉토리의 파일 및 폴더 전체 모음.
[^6]: 레이어 캐시 (Layer Cache): 이전에 빌드한 Dockerfile 지시어의 실행 결과 레이어를 재사용하여 빌드 시간을 단축하는 기능.
