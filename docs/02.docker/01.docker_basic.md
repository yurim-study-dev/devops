# 1. 가상화 기술 및 Docker 기본 원리

## 1.1 서버 가상화 발전 과정 및 필요성

- 온프레미스 인프라 환경에서 단일 서버에 하나의 운영체제와 단일 애플리케이션을 구동할 경우 시스템 자원 활용률이 크게 저하되는 비효율이 발생함.
- 물리 서버 자원의 효율적 분배와 종속성 격리를 달성하기 위해 가상화 기술을 도입함.

## 1.2 가상 머신(VM) 및 컨테이너 가상화 구조

- 단일 물리 서버 환경에서 복수의 애플리케이션을 직접 구동할 경우, 공유 시스템 라이브러리 패키지의 버전 충돌이 발생하고 특정 프로세스의 호스트 자원 독점으로 인해 전체 시스템 안정성이 저해되는 한계가 존재함.
- 이러한 물리 인프라 자원의 격리 한계와 환경 이식성 [^1] 문제를 해결하고 독립적인 애플리케이션 구동 환경을 제공하기 위해 가상화 기술을 활용함.

### 1.2.1 가상 머신 (Virtual Machine) 가상화 구조
- 물리적 하드웨어 상위에 하이퍼바이저 [^2] (Hypervisor)를 두고, 그 위에 독립된 게스트 운영체제(Guest OS)를 각각 설치하여 애플리케이션을 실행하는 구조로 AWS EC2 인스턴스가 대표적인 VM 방식의 가상화 환경임.
- 각 VM마다 별도의 OS 커널 [^3] (Kernel), 바이너리, 시스템 라이브러리가 포함되므로 디스크 용량이 대용량(수 GB ~ 수십 GB)이며 부팅 시간이 수 분 소요됨.
- 하드웨어 자원 에뮬레이션 [^4] (Emulation) 처리로 인해 CPU 및 메모리 성능 오버헤드가 발생함.

### 1.2.2 컨테이너 (Container) 가상화 구조
- 컨테이너 가상화는 호스트 운영체제(Host OS)의 커널을 공유하면서, 별도의 게스트 OS 없이 프로세스 수준에서 애플리케이션 실행 환경을 격리하여 구동하는 방식임.
- 게스트 OS가 존재하지 않으므로 이미지 크기가 작고(수 MB ~ 수백 MB), 부팅 시간이 수 초 이내로 신속함.
- 커널 직접 호출 방식을 사용하므로 하이퍼바이저 오버헤드가 제거되어 베어메탈 [^5] (Bare-metal)에 근접한 실행 성능을 확보함.

## 1.3 Docker 플랫폼 개요 및 기술적 의의

### 1.3.1 Docker 플랫폼 정의
- 2013년 dotCloud(현 Docker Inc.)에서 오픈소스로 공개한 컨테이너 기반 가상화 플랫폼.
- 리눅스 커널의 자원 격리 기술(cgroups, namespaces)을 바탕으로 애플리케이션을 경량화된 컨테이너 이미지 형태로 패키징하여 배포 및 구동하도록 지원함.

### 1.3.2 소프트웨어 공급망(Software Supply Chain)의 혁신
- 소스 코드 작성 -> 컨테이너 이미지 빌드 -> 중앙 레지스트리 저장 -> 운영 서버 배포로 이어지는 자동화된 CI/CD [^6] (Continuous Integration / Continuous Deployment) 파이프라인의 핵심 기본 실행 단위로 정착함.
- 로컬 개발 환경과 검증/운영 환경 간 배포 이식성을 제공하여 소프트웨어 배포 주기를 단축함.

# 2. Docker 설치 및 실행 환경 구축

- 참고: https://www.docker.com/products/docker-desktop/

## 2.1 Docker Desktop 개요
- Docker Desktop은 Windows, macOS 환경에서 리눅스 컨테이너 개발 및 실행 환경을 통합 관리하기 위한 데스크톱 애플리케이션.
- Docker Engine, Docker Client, Docker Compose 등 주요 컨테이너 관리 인터페이스를 단일 패키지로 제공함.

## 2.2 Windows 환경

### 2.2.1 WSL (Windows Subsystem for Linux) 2
- Docker Desktop은 Windows 환경에서 리눅스 커널 기반 컨테이너를 구동하기 위한 핵심 백엔드로 WSL 2 엔진을 활용함.
- Docker Desktop 설치 및 구동 전 Windows 가상화 기능인 WSL 2를 사전에 활성화하고 설치해야 함.
  - 미리 설치하지 않을 경우 Docker Desktop 설치 시 자동으로 설치됨.
- PowerShell(관리자 권한)에서 `wsl --install` 명령을 실행하여 WSL 2 환경을 구축.

### 2.2.2 Docker Desktop 설치 파일 다운로드 및 실행
- [Docker 공식 웹사이트](https://docs.docker.com/desktop/setup/install/windows-install/)에서 `Docker Desktop for Windows - x86_64` 버튼을 클릭하여 설치 파일을 다운로드.

### 2.2.3 시스템 재부팅 및 구동 확인
- 시스템 재부팅 후 Docker Desktop을 구동하여 상태 표시줄에서 정상 작동 메시지를 확인.

## 2.3 macOS 환경

### 2.3.1 아키텍처별 설치 파일 선택 및 다운로드
- [Docker 공식 웹사이트](https://docs.docker.com/desktop/setup/install/mac-install/)에서 칩셋 아키텍처에 맞는 설치 파일을 다운로드.
- Apple Silicon (M1/M2/M3/M4) 칩셋 환경은 `Docker Desktop for Mac with Apple Silicon` 선택해서 다운로드.
- Intel 칩셋 환경은 `Docker Desktop for Mac with Intel chip` 선택해서 다운로드.

### 2.3.2 애플리케이션 설치 및 등록
- 다운로드된 `.dmg` 파일을 실행하여 `Docker.app` 아이콘을 `Applications` (응용 프로그램) 폴더로 드래그 앤 드롭.

### 2.3.3 가상화 엔진 및 리소스 할당 설정
- Docker Desktop 실행 후 Settings -> General 메뉴에서 Use Virtualization framework 옵션을 선택.
- Resources 메뉴에서 CPU 및 Memory 할당량을 환경에 맞추어 설정.

### 2.3.4 시스템 구동 및 정상 작동 확인
- macOS 상단 메뉴 바에서 Docker 데몬 아이콘이 정상 상태로 활성화되었는지 확인.

## 2.4 Linux(Amazon Linux) 환경 Docker Engine 설치 및 데몬 설정

- 리눅스(Amazon Linux) 환경에서는 패키지 관리자 [^7]를 통해 Docker Engine 패키지를 설치하고 데몬 서비스를 구동.

### 2.4.1 패키지 업데이트 및 Docker 엔진 설치
```bash
# 시스템 패키지 목록 업데이트
sudo yum update -y

# Docker Engine 패키지 설치
sudo yum install -y docker
```

### 2.4.2 Docker 데몬 서비스 활성화 및 상태 확인
```bash
# Docker 데몬 자동 시작 등록 및 서비스 구동
sudo systemctl enable --now docker

# Docker 데몬 작동 상태 확인
sudo systemctl status docker
```

## 2.5 설치 상태 검증 및 non-root 권한 설정

- Linux 환경에서 기본 설치 상태에서는 `sudo` 권한을 가진 사용자만 Docker 데몬 Unix 소켓 [^8]에 접근 가능하므로, 일반 사용자 계정을 `docker` 그룹에 포함시켜 보안 권한을 적용.

### 2.5.1 사용자 권한 부여 및 시스템 적용
```bash
# 현재 사용자 계정을 docker 그룹에 추가하여 sudo 없이 실행 허용
sudo usermod -aG docker $USER

# 그룹 변경 사항을 현재 쉘 세션에 즉시 적용 (또는 재로그인)
newgrp docker
```

### 2.5.2 샘플 컨테이너 실행 및 설치 검증
```bash
docker run hello-world
```

# 3. Docker 아키텍처 및 핵심 구성 요소

## 3.1 Docker Client 및 Daemon
- Docker Daemon (`dockerd`) [^9]: 호스트 시스템에 상주하며 컨테이너 생성, 실행, 이미지 빌드, 네트워크/볼륨 관리를 총괄 수행하는 백그라운드 프로세스.
- Docker Client (`docker`): 사용자가 CLI 명령어를 입력하면 REST API [^10] 를 통해 Docker Daemon으로 요청을 전달하는 인터페이스 도구.

## 3.2 Docker Image 및 Container
- Docker Image: 컨테이너를 생성하기 위한 읽기 전용 템플릿으로, 애플리케이션 바이너리, 설정 파일, 종속 라이브러리가 레이어 구조로 정적으로 저장됨.
- Docker Container: Docker Image가 실행되어 독립된 메모리와 파일 시스템 공간을 할당받은 런타임 [^11] 프로세스 실행 상태.

## 3.3 Docker Registry
- 컨테이너 이미지를 저장, 버전 관리 및 공유하기 위한 중앙 저장소 시스템.
- 주요 레지스트리 종류
  - Docker Hub: Docker 기본 공용 중앙 저장소 (`docker.io`). 레지스트리주소 생략시 사용되는 기본값.
  - GHCR (GitHub Container Registry): GitHub 계정 권한 및 CI/CD 파이프라인과 연동되는 레지스트리 서비스 (`ghcr.io`).
  - Amazon ECR (Amazon Elastic Container Registry): AWS 클라우드 인프라 기반의 관리형 사설 이미지 저장소 (`[aws_account_id].dkr.ecr.[region].amazonaws.com`).

# 4. Docker CLI 명령어를 활용한 컨테이너 기초

- Docker CLI(Command Line Interface): 사용자가 터미널에서 `docker` 명령어와 옵션을 입력하여 Docker 데몬과 통신하고 컨테이너 및 이미지의 상태를 제어하는 핵심 도구.

## 4.1 이미지 조작 및 레지스트리 연동 CLI 명령어

### 4.1.1 이미지 검색 및 다운로드

#### 1) `docker search [옵션] [키워드]`
- Docker Hub 중앙 레지스트리에 등록된 공용 이미지 목록을 키워드로 검색함.
- 주요 옵션
  - `-f [조건]` (`--filter`): 검색 결과를 별점(stars), 공식 검증 여부(is-official) 등의 조건으로 필터링함.
  - `-n [개수]` (`--limit`): 검색 결과의 최대 출력 개수를 지정함 (기본값: 25).
- 예시
  ```bash
  # 1. 기본 검색 (키워드로 Docker Hub 저장소 이미지 단순 검색)
  docker search mysql

  # 2. 필터링 및 개수 제한 옵션 지정 검색 (공식 검증 이미지 중 별점 100개 이상만 최대 5개 검색)
  docker search -f "is-official=true" -f "stars=100" -n 5 mysql
  ```

- `docker search` CLI 명령어는 이미지 존재 여부나 공식 검증 유무를 터미널에서 빠르게 확인할 때 사용함.
- 다만 지원되는 세부 태그(버전) 목록이나 설정 방법을 보여주지 않으므로, 실제로는 지원 태그 목록, 필수 환경변수 설정법 및 사용 설명서(Documentation)를 정확히 파악할 수 있는 Docker Hub 웹사이트(https://hub.docker.com) 접속 검색 방식을 주로 활용함.

#### 2) `docker pull [옵션] [이미지명]:[태그]`
- 지정한 이미지와 특정 태그(버전)를 중앙 저장소로부터 로컬 호스트로 다운로드함.
- 주요 옵션
  - `-a` (`--all-tags`): 해당 이미지의 등록된 모든 태그 버전을 한 번에 다운로드함.
- 이미지 이름 표기 규칙 (Naming Convention) 및 기본값
  - 표준 형식: `[레지스트리주소/][소유자명/]이미지명:태그` (예: `docker.io/library/mysql:9.7`)
  - 레지스트리 주소 생략 시: Docker Hub 기본 공용 저장소인 `docker.io`가 지정됨.
  - 소유자명 생략 시: Docker Hub 공식 검증 이미지인 `library/`가 지정됨.
  - 태그 생략 시: 최신 버전을 의미하는 기본 태그`latest`가 지정됨.
- 예시
  ```bash
  # 1. 기본 다운로드 (태그 생략 시 최신 latest 버전 다운로드)
  docker pull ubuntu

  # 2. 특정 태그 지정 다운로드 (mysql 9.7 버전 지정 다운로드)
  docker pull mysql:9.7
  ```

### 4.1.2 로컬 이미지 관리 및 태그 지정

#### 1) `docker image ls [옵션]`
- 로컬 저장소에 다운로드되어 있는 Docker 이미지 목록(REPOSITORY, TAG, IMAGE ID, CREATED, SIZE 등)을 조회함 (`docker images`와 동일).
- 예시
  ```bash
  docker image ls
  ```

#### 2) `docker tag [원본이미지]:[태그] [새이미지]:[새태그]`
- 기존 이미지에 새로운 별칭이나 원격 레지스트리 주소가 포함된 라벨 태그를 추가함.
- 예시
  ```bash
  # 1. 기본 태그 추가 (기존 mysql:9.7 이미지에 spring-board/mysql 별칭 추가)
  docker tag mysql:9.7 spring-board/mysql

  # 2. 원격 레지스트리 주소 포함 태그 추가 (사용자 계정/레지스트리 식별명 태그 지정)
  docker tag spring-board/mysql myregistry.com/spring-board/mysql:1.0
  ```

#### 3) `docker image rm [옵션] [이미지ID|이미지명]`
- 지정한 로컬 이미지를 호스트 시스템에서 삭제함 (`docker rmi`와 동일).
  - 이미지 ID는 전체 ID 대신 앞 3~4자리만 지정하여 삭제할 수 있음.
- 주요 옵션
  - `-f` (`--force`): 정지되거나 참조 중인 컨테이너가 있더라도 이미지를 강제로 삭제함.

- 예시
  ```bash
  docker image rm mysql:9.7
  ```

## 4.2 컨테이너 라이프사이클 통제 및 상태 관리 CLI 명령어

### 4.2.1 컨테이너 라이프사이클 제어 (생성, 구동, 정지, 시작, 재시작, 삭제)

#### 1) `docker create [옵션] [이미지명]`
- 이미지를 기반으로 새로운 컨테이너를 생성만 하고 시작하지는 않음 (정지된 Created 상태로 생성).
- 주요 공통 설정 옵션 (`run` 명령어와 공통 사용)
  - `--name [이름]`: 컨테이너에 고유 식별 이름을 부여함.
  - `-p [호스트포트]:[컨테이너포트]` (`--publish`): 호스트의 포트와 컨테이너 내부 포트를 연결(포트 매핑)함.
  - `-v [호스트경로]:[컨테이너경로]` (`--volume`): 호스트 디렉터리 또는 볼륨을 컨테이너 내부에 연결함.
  - `-e [KEY=VAL]` (`--env`): 컨테이너 내부 환경변수를 설정함.
- 예시
  ```bash
  # 1. 기본 생성 (옵션 없이 이미지명으로만 정지 상태 컨테이너 생성)
  docker create docker/getting-started

  # 2. 포트 매핑 및 이름 지정 생성 (이름 부여 및 포트 매핑 옵션 적용)
  docker create --name sample-web -p 80:80 docker/getting-started

  # 3. 환경변수(-e) 지정 생성 (MySQL 루트 비밀번호 환경변수 설정 포함 정지 상태 컨테이너 생성)
  docker create --name db-server -p 3306:3306 -e MYSQL_ROOT_PASSWORD=secret mysql:9.7
  ```

#### 2) `docker start [옵션] [컨테이너ID|이름]`
- 정지되어 있는 컨테이너 프로세스를 시작함 (별도 옵션 지정 없이 실행 시 백그라운드 상태로 시작됨).
- 주요 옵션
  - `-a` (`--attach`): 컨테이너 프로세스를 시작하면서 표준 출력 및 에러(stdout/stderr) 스트림을 현재 터미널 세션에 직접 연결함 (포그라운드 시작).
- 예시
  ```bash
  # 1. 기본 시작 (정지된 컨테이너를 백그라운드 프로세스로 시작)
  docker start sample-web

  # 2. 대화형 인터랙티브 시작 옵션 적용 (-a 옵션으로 컨테이너 출력 스트림을 터미널에 연결하며 시작)
  docker start -a sample-web
  ```

#### 3) `docker run [옵션] [이미지명]`
- 이미지를 기반으로 새로운 컨테이너를 생성하고 즉시 시작함 (`docker create` + `docker start` 결합 수행).
- 별도 옵션 지정 없이 실행 시 터미널 스트림이 직접 연결되는 포그라운드 상태로 구동됨.
- `docker create`에서 사용하는 모든 공통 설정 옵션(`--name`, `-p`, `-v`, `-e` 등)을 동일하게 지원함.
- 주요 실행 통제 옵션
  - `-d` (`--detach`): 컨테이너를 시작할 때 표준 입출력을 분리하여 백그라운드 데몬 프로세스로 구동함.
  - `--rm`: 컨테이너 실행 종료 시 호스트 시스템에서 자동으로 정지 및 삭제함. (일회성 실행)
- `docker start`와 `docker run` 기본 실행 모드 비교
  - 백그라운드 실행: `docker start` (기본값) == `docker run -d`
  - 포그라운드 실행: `docker start -a` == `docker run` (기본값)
- 예시
  ```bash
  # 1. 기본 실행 (옵션 없이 포그라운드 세션으로 생성 및 실행)
  docker run docker/getting-started

  # 2. 주요 옵션 지정 실행 (백그라운드 구동 -d, 이름 부여, 포트 매핑 옵션 동시 적용)
  docker run -d --name sample-web2 -p 81:81 docker/getting-started

  # 3. 환경변수(-e) 지정 백그라운드 구동 (MySQL 비밀번호 환경변수를 전달하여 즉시 생성 및 구동)
  docker run -d --name db-server2 -p 3307:3306 -e MYSQL_ROOT_PASSWORD=secret mysql:9.7
  ```

#### 4) `docker stop [옵션] [컨테이너ID|이름]`
- 실행 중인 컨테이너 프로세스에 정지 신호(SIGTERM)를 전달하여 안전하게 정지시킴.
- 주요 옵션
  - `-t [초]` (`--time`): 컨테이너 프로세스에 정지 신호(SIGTERM)를 보낸 후 강제 종료(SIGKILL)하기까지 대기할 타임아웃 시간을 초 단위로 지정함 (기본값: 10초).
- 예시
  ```bash
  # 1. 기본 정지 (SIGTERM 전송 후 일정 시간 대기하여 안전하게 프로세스 정지)
  docker stop sample-web2

  # 2. 타임아웃 옵션 지정 정지 (-t 옵션으로 정지 대기 시간을 5초로 지정)
  docker stop -t 5 sample-web2
  ```

#### 5) `docker restart [옵션] [컨테이너ID|이름]`
- 컨테이너 프로세스를 재시작함.
- 주요 옵션
  - `-t [초]` (`--time`): 컨테이너 프로세스 재시작 전 안전한 프로세스 정지를 위해 대기할 타임아웃 시간을 초 단위로 지정함 (기본값: 10초).
- 예시
  ```bash
  # 1. 기본 재시작 (컨테이너 프로세스 즉시 재부팅)
  docker restart sample-web2

  # 2. 타임아웃 옵션 지정 재시작 (-t 옵션으로 3초 후 프로세스 재시작)
  docker restart -t 3 sample-web2
  ```

#### 6) `docker rm [옵션] [컨테이너ID|이름]`
- 정지 상태의 컨테이너를 호스트 시스템에서 완전히 삭제함.
- 주요 옵션
  - `-f` (`--force`): 정지 상태가 아닌 실행 중인 컨테이너를 강제 정지 후 삭제함.
- 예시
  ```bash
  docker rm sample-web2
  ```

### 4.2.2 컨테이너 상태 조회 및 로그 모니터링

#### 1) `docker ps [옵션]`
- 현재 실행 중인 컨테이너 목록(CONTAINER ID, IMAGE, COMMAND, PORTS, NAMES 등)을 조회함.
- 주요 옵션
  - `-a` (`--all`): 정지되거나 종료된 컨테이너를 포함한 전체 목록을 출력함.
- 예시
  ```bash
  docker ps
  ```

#### 2) `docker logs [옵션] [컨테이너ID|이름]`
- 컨테이너 내부 프로세스가 표준 출력(stdout) 및 표준 에러(stderr)로 내보낸 로그 기록을 확인함.
- 주요 옵션
  - `-f` (`--follow`): 로그 출력을 실시간 스트리밍으로 지속 모니터링함.
- 예시
  ```bash
  # 1. 기본 로그 조회 (현재 시점까지 누적된 로그 기록을 일회성 출력)
  docker logs sample-web

  # 2. 실시간 스트리밍 옵션 적용 (-f 옵션으로 로그 출력을 터미널에 지속 스트리밍)
  docker logs -f sample-web
  ```

### 4.2.3 컨테이너 내부 진입 및 인터랙티브 제어

#### 1) `docker exec [옵션] [컨테이너ID|이름] [명령어]`
- 실행 중인 컨테이너 내부에서 새로운 명령어를 추가로 수행함.
- 주요 옵션
  - `-i` (`--interactive`): 표준 입력(stdin) 스트림을 열어 두어 사용자의 키보드 입력을 컨테이너 내부 프로세스로 지속 전달함.
  - `-t` (`--tty`): 가상 터미널(Pseudo-TTY)을 할당하여 컨테이너 내부의 쉘(`/bin/sh` 또는 `/bin/bash`)과 대화형 터미널 통신 세션을 연결함.
  - `-w [경로]` (`--workdir`): 명령어를 수행할 컨테이너 내부의 작업 디렉터리 위치를 지정함.
- 옵션 결합 및 분리 표기 규칙
  - 단축 플래그 옵션 결합: 별도의 인자 값이 필요 없는 플래그 옵션인 `-i`와 `-t`는 하나로 묶어 `-it` 형태로 결합하여 작성함.
  - 인자 동반 옵션 분리: 뒤에 디렉터리 경로 인자가 동반되는 `-w` 옵션은 구문 오류 방지 및 가독성을 위해 `-it -w /etc` 형태로 분리하여 작성함.
- 예시
  ```bash
  # 1. 옵션 없는 단발성 명령 실행 (컨테이너 내부 /etc 디렉터리 파일 목록 단순 조회, Git Bash 호환 //etc 지정)
  docker exec sample-web ls //etc

  # 2. 대화형 옵션 결합 실행 (-it 옵션으로 내부 대화형 쉘 접속, Git Bash 호환 //bin/sh 지정)
  docker exec -it sample-web //bin/sh

  # 3. 작업 디렉터리 옵션 분리 실행 (-it 및 -w //etc 옵션으로 시스템 설정 경로 접속)
  docker exec -it -w //etc sample-web //bin/sh
  ```

## 4.3 Docker 네트워크 드라이버 운용 (bridge, host, overlay)

- Docker 네트워크는 컨테이너 간 통신 및 호스트 외부 통신망 격리를 제어하는 핵심 서브시스템으로, 상황에 맞춰 다양한 네트워크 드라이버를 제공함.

### 4.3.1 Docker 네트워크 필요성
- 프로세스 및 환경 격리 해제와 통신 채널 구축: 컨테이너는 기본적으로 네트워크 네임스페이스(Network Namespace) 기술을 통해 호스트 및 타 컨테이너와 완전 격리됨. 독립된 컨테이너 내부의 애플리케이션(예: Spring Boot)이 외부 데이터베이스(예: MySQL)와 연동되려면 가상 인터페이스 기반의 네트워크 통로가 필수적임.
- 서비스 네트워크 분리와 보안성 강화: 외부 인터넷망에 노출해야 하는 웹 서버(Front-end, API Gateway)와 외부 노출이 차단되어야 하는 내부 데이터베이스/캐시 서버를 개별 가상 네트워크로 분리할 수 있음. 이를 통해 민감 데이터에 대한 무단 접근을 방지하고 공격 노출 영역(Attack Surface)을 최소화함.
- 동적 IP 변환에 따른 식별 문제 해결 (내장 DNS 기반 디스커버리): 컨테이너는 생성 및 재시작 시 가상 IP 주소가 동적으로 변경될 수 있음. Docker 네트워크가 제공하는 내장 DNS 서버를 활용하면 고정되지 않은 IP 대신 컨테이너 이름(Container Name)이나 별칭(Alias)으로 안전하게 상호 탐색 및 통신을 수행함.
- 호스트 포트 자원 충돌 방지 및 선택적 노출: 여러 컨테이너가 동일한 포트(예: 80, 3306)를 내부적으로 사용하더라도 가상 사설 네트워크 대역에서 각각 독자적인 포트를 점유하므로 포트 충돌이 발생하지 않음. 필요한 포트만 선택적으로 호스트 포트 바인딩(-p)을 수행하여 외부 통신을 허용함.

### 4.3.2 Bridge Network
- 단일 호스트 내부에서 컨테이너 간 가상 사설 네트워크 격리 환경을 형성함.

#### 1) 기본 브릿지
- 컨테이너 생성 시 네트워크를 지정하지 않으면 `bridge`라는 이름의 기본 브릿지가 할당되며, 컨테이너 IP 주소를 통해서만 상호 통신이 가능함.
- 다른 컨테이너와 통신할 필요가 없는 단일 컨테이너 환경이거나 네트워크 설정 없이 빠르게 컨테이너를 구동해서 외부 인터넷과 통신하는 작업을 테스트하는 용도

#### 2) 사용자 정의 브릿지
- 사용자가 직접 생성한 브릿지 네트워크로, IP 주소뿐만 아니라 컨테이너 이름(Container Name)을 기반으로 자동 DNS 주소 변환(Name Resolution)을 제공함.
- `docker network create [네트워크명]` 명령어를 사용하여 독립된 사용자 정의 브릿지 네트워크를 생성함.
- 동작 원리: Docker 엔진이 내장 DNS 서버(127.0.0.11)를 구동하여 컨테이너 내부에 자동 등록하고, 컨테이너 이름을 가상 IP 주소로 동적 매핑함.
- 동일한 사용자 정의 브릿지에 속한 컨테이너들은 컨테이너 이름으로 서로를 식별하고 통신할 수 있어 백엔드-DB 연동에 필수적임.
- 예시
  ```bash
  # 1. 사용자 정의 브릿지 네트워크 생성
  docker network create myapp-net

  # 2. 사용자 정의 브릿지에 백엔드 DB 컨테이너 연결 구동 (DBeaver 등 호스트 외부 접속용 포트 매핑 -p 3306:3306 포함)
  docker run -d --name db-server --network myapp-net -p 3306:3306 -e MYSQL_ROOT_PASSWORD=secret mysql:9.7

  # 3. 동일한 브릿지에 spring-board 애플리케이션 컨테이너 구동 후 DB 컨테이너 이름(db-server)으로 연동
  docker run -d --name spring-board-app --network myapp-net -p 80:8080 spring-board:1.0
  ```

### 4.3.3 Host Network
- 컨테이너의 네트워크 격리(Network Namespace)를 제거하고 호스트의 네트워크 인터페이스를 직접 공유하여 사용하는 방식.
- 별도의 포트 매핑 옵션(`-p`)이 필요 없으며, 컨테이너 프로세스가 호스트의 포트를 직접 점유함.
- 가상 브릿지 조작 및 NAT 변환 과정이 생략되므로 네트워크 I/O 성능 오버헤드가 최소화됨.
  - 호스트 상의 기존 포트와 충돌 가능성 및 macOS/Windows 가상화 환경에서의 작동 제약이 존재하므로 주의가 필요함.
- 대부분의 경우 보안 격리와 포트 관리가 용이한 Bridge Network가 표준으로 사용되며, Host Network는 극단적인 네트워크 I/O 성능 극대화가 필요한 예외적인 케이스로 한정하여 활용함.

```bash
# 호스트 네트워크 모드로 웹 서버 구동 (호스트 80 포트를 직접 점유)
docker run -d --name host-web --network host nginx:alpine
```

### 4.3.4 Overlay Network
- 서로 다른 물리 서버(또는 VM 노드)에 존재하는 컨테이너들을 단일 가상 사설 네트워크 서브넷으로 연결하는 분산 네트워크 드라이버.
- Docker Swarm [^12] 또는 쿠버네티스 [^13] (Kubernetes) 환경에서 다중 노드 간 컨테이너 분산 통신을 구축할 때 활용됨.
- VXLAN(Virtual Extensible LAN) 캡슐화 기술을 바탕으로 암호화된 터널링 통신을 지원함.

### 4.3.5 Docker 네트워크 주요 CLI 명령어

#### 1) `docker network ls`
- 호스트 내에 존재하는 Docker 네트워크 목록(bridge, host, none 등)을 조회함.
- 예시
  ```bash
  docker network ls
  ```

#### 2) `docker network inspect [네트워크명]`
- 특정 네트워크의 상세 가상 서브넷 정보 및 연결된 컨테이너 IP 주소를 확인함.
- 예시
  ```bash
  docker network inspect myapp-net
  ```

#### 3) `docker network connect [옵션] [네트워크명] [컨테이너명]`
- 실행 중인 컨테이너를 지정한 네트워크에 추가로 연결함.
- 컨테이너를 정지 후 다시 시작하거나 재시작해도 연결 상태가 영구 유지됨.
- 예시
  ```bash
  docker network connect myapp-net sample-web
  ```

#### 4) `docker network disconnect [옵션] [네트워크명] [컨테이너명]`
- 실행 중인 컨테이너를 지정한 네트워크에서 연결 해제함.
- 주요 옵션
  - `-f` (`--force`): 실행 중인 컨테이너의 네트워크 연결을 강제로 해제함.
- 예시
  ```bash
  docker network disconnect myapp-net sample-web
  ```

#### 5) `docker network prune [옵션]`
- 현재 연결된 컨테이너가 없는 고립된 네트워크를 일괄 삭제 및 정리함.
- 주요 옵션
  - `-f` (`--force`): 별도의 삭제 승인 확인 절차 없이 즉시 강제로 정리함.
- 예시
  ```bash
  docker network prune
  ```

## 4.4 데이터 지속성 통제 (Bind Mounts vs Named Volumes)

- 컨테이너 내부 쓰기 레이어는 컨테이너 정지 및 삭제 시 데이터가 소멸되므로, 영구 보존이 필요한 데이터를 위해 데이터 지속성 메커니즘이 필요.
- 컨테이너 구동 후 애플리케이션이 실행되면서 생성되는 파일들을 호스트의 파일 시스템에 보관해서 컨테이너가 삭제 되더라도 파일이 유지되도록 하는 목적.

### 4.4.1 Named Volumes

#### 1) Named Volumes 작동 원리 및 특징
- Docker 데몬이 직접 관리하는 전용 영역(`/var/lib/docker/volumes/`)에 독립된 데이터 볼륨을 생성하고 컨테이너와 연동하는 방식.
- 호스트의 디렉터리 구조에 의존하지 않으며 복수 컨테이너 간 데이터 공유 및 데이터베이스 파일 영구 보존에 적합함.
- OS별 실제 저장 위치 및 호스트 접근 특징
  - Linux 호스트: 호스트 파일 시스템의 `/var/lib/docker/volumes/[볼륨명]/_data` 경로에 직접 저장됨.
  - Windows (Docker Desktop): WSL 2 가상 머신 내부 영역에 저장되며, 윈도우 탐색기 주소창에 `\\wsl$` 입력 후 `docker-desktop -> mnt -> docker-desktop-disk -> data -> docker -> volumes -> [볼륨명] -> _data` 순으로 이동해서 물리 데이터를 확인할 수 있음.
  - macOS (Docker Desktop): 경량 Linux 가상 머신(VM) 내부의 `/var/lib/docker/volumes/[볼륨명]/_data` 경로에 저장되며, macOS 호스트 상에서는 가상 디스크 파일(`Docker.raw`) 내부에 저장되므로 Finder에 직접 노출되지 않고 가상 머신 디버그 쉘을 통해 접근함.

#### 2) 볼륨 관리 CLI 명령어 (`docker volume`)
- `docker volume create [볼륨명]`: 독립된 데이터 볼륨을 새로 생성함.
- `docker volume ls`: 호스트 내에 생성된 볼륨 목록을 조회함.
- `docker volume inspect [볼륨명]`: 특정 볼륨의 상세 저장 경로 및 정보를 확인함.
- `docker volume rm [볼륨명]`: 사용하지 않는 단일 볼륨을 지정하여 삭제함.
- `docker volume prune [옵션]`: 현재 어떤 컨테이너에도 연결되어 있지 않은 고립된 찌꺼기 익명 볼륨 및 미사용 볼륨을 일괄 정리함.
  - `-f` (`--force`): 별도의 삭제 승인 확인 절차 없이 즉시 강제로 정리함.
- 예시
  ```bash
  # 1. DB 데이터 전용 볼륨 및 게시판 첨부파일 전용 볼륨 생성
  docker volume create spring-board-db-data

  # 2. DB 컨테이너에 Named Volume 마운트 구동(mysql은 기본으로 var/lib/mysql 폴더에 데이터를 저장함)
  docker run -d --name db-server --network myapp-net -p 3306:3306 -v spring-board-db-data:/var/lib/mysql -e MYSQL_DATABASE=board_db -e MYSQL_ROOT_PASSWORD=root mysql:9.7

  # 3. Spring Board 컨테이너에 Named Volume 마운트 구동
  docker run -d --name spring-board --network myapp-net -p 80:8080 -v spring-board-file-uploads:/app/uploads {dockerhub-username}/spring-board:1.0

  # 4. 볼륨 목록 조회 및 상세 정보 확인
  docker volume ls
  docker volume inspect spring-board-file-uploads

  # 5. 개별 볼륨 삭제 및 미사용 찌꺼기 볼륨 일괄 강제 정리
  docker volume rm spring-board-file-uploads
  docker volume prune -f
  ```

### 4.4.2 Bind Mounts
- 호스트 파일 시스템의 특정 경로(Absolute Path)를 컨테이너 내부 디렉터리 경로와 1대1로 직접 마운트하여 실시간 공유하는 메커니즘.
- 호스트 환경의 첨부파일 업로드 디렉터리 연동, 로그 파일 저장 등에 사용.
- Bind Mounts 기본 문법 및 사용법
  - 기본 형식: `-v "[호스트_절대경로]:[컨테이너_내부경로]"` (예: `-v "${PWD}/uploads:/app/uploads"`)
  - 읽기 전용 보안 옵션: 컨테이너 내부에서 수정이 불가능하도록 설정 시 끝에 `:ro` 지정 (예: `-v "${PWD}/config/app.properties:/app/config/app.properties:ro"`)
- `${PWD}` (Print Working Directory / Present Working Directory) 환경 변수 활용: PWD는 Present Working Directory(현재 작업 디렉터리) 또는 Print Working Directory의 약어로, 현재 터미널 쉘 세션이 위치한 작업 디렉터리의 절대 경로를 동적으로 반환함.
- Docker 바인드 마운트 옵션(`-v`)은 호스트 디렉터리 지정 시 상대 경로(예: `./uploads`)를 지원하지 않고 절대 경로를 요구하므로 `${PWD}` 환경 변수를 조합하여 사용함.
- Windows Git Bash 환경의 `${PWD}` 경로 변환 충돌 및 해결책
  - MSYS2 [^14] 경로 자동 변환 충돌 원인: Windows Git Bash의 `${PWD}`가 반환하는 리눅스 스타일 절대 경로(`/c/...`)를 MSYS2 런타임이 Windows 경로 포맷(`C:\...`)으로 강제 자동 변환하는 과정에서, 마운트 옵션의 콜론(`:`) 및 컨테이너 내부 경로와 결합되어 구문 오류가 발생함.
  - `MSYS_NO_PATHCONV=1` 환경 변수의 역할: MSYS2 런타임의 인자 자동 경로 변환 기능을 비활성화(Disable)하여 `${PWD}`가 반환하는 리눅스 스타일 경로(`/c/...`)를 원본 그대로 `docker` CLI 프로세스로 전달함. (Windows용 Docker CLI 엔진은 `/c/...` 형태의 호스트 드라이브 경로를 Windows 파일 시스템 경로로 자체 인식하므로 바인드 마운트가 정상 수행됨).
  - 컨테이너 내부에서 사용할 실제 리눅스 경로를 표현하는 명령어 바로 앞에 `MSYS_NO_PATHCONV=1`을 붙여 구동.

- 예시
  ```bash
  # 1. 호스트 시스템에 첨부파일 저장용(uploads) 및 로그 저장용(logs) 디렉터리 생성(프로젝트 루트에서 실행)
  mkdir uploads logs

  # 2. 업로드 및 로그 디렉터리 바인드 마운트 구동 (MSYS_NO_PATHCONV=1 환경 변수 적용)
  MSYS_NO_PATHCONV=1 docker run -d --name spring-board-4 --network board-net -p 81:8080 \
    -v "${PWD}/uploads:/app/uploads" \
    -v "${PWD}/logs:/app/logs" \
    {dockerhub-username}/spring-board:1.0
  ```

## 5.2 기존 실습 리소스 조회 및 전체 삭제
- 실습 환경을 깨끗하게 초기화하기 위해 기존의 모든 컨테이너, 이미지, 네트워크 및 Named Volumes 목록을 먼저 확인한 후 전부 일괄 삭제함.
- 명령어 문법
  - 서브셸 구문(`$(명령어)`): 괄호 내부 명령어의 실행 결과(예: 전체 컨테이너/이미지/볼륨 ID 목록, -q 옵션을 지정할 경우 ID만 조회)를 외부 명령어의 인자로 동적으로 전달함.

  - 예외 보장 구문(`|| true`): 앞선 삭제 명령어가 에러(Exit Code 1)로 종료되더라도 스크립트 실행이 중단되지 않고 다음 명령어로 정상 진행되도록 보장함.

```bash

docker images
docker network ls
docker volume ls

# 2. 모든 기존 컨테이너 강제 중지 및 전체 삭제

# 3. 모든 기존 이미지 강제 전체 삭제
docker rmi -f $(docker images -q) 2>/dev/null || true

# 4. 모든 기존 Named Volumes 및 미사용 네트워크 전체 삭제
```

## 6.1 Nginx 리버스 프록시 연동 및 다중 컨테이너 환경 구축

- 앞단에 Nginx 웹 서버를 리버스 프록시 및 로드 밸런서로 배치하고, 뒷단에 복수의 Spring Board 애플리케이션 컨테이너를 띄워 부하 분산 및 무중단 배포 실습 환경을 구축함.
- Nginx: 동시 트래픽 처리에 특화된 고성능 오픈소스 웹 서버이자, 최앞단에서 클라이언트 요청을 중계 및 분산하는 대표적인 리버스 프록시 및 로드 밸런싱 소프트웨어 엔진.
  - Nginx 공식 문서: https://nginx.org/en/docs/
  - Nginx 공식 한글 문서 (NGINX Store): https://nginxstore.com/blog/nginx/

## 6.2 Nginx 리버스 프록시 아키텍처 및 로드 밸런싱 원리

### 6.2.1 리버스 프록시 및 로드 밸런싱 핵심 개념
- 리버스 프록시(Reverse Proxy) 역할: 클라이언트의 모든 HTTP 요청(80 포트)을 최앞단에서 수신한 후, 내부 가상 사설 네트워크(`board-net`)에 존재하는 복수의 애플리케이션 컨테이너로 요청을 안전하게 중계 전달함.
- 로드 밸런싱 및 고가용성 [^15] 보장: 라운드 로빈 [^16] (Round Robin) 알고리즘을 기반으로 트래픽을 각 컨테이너로 균등하게 분산하고, 장애가 발생한 인스턴스를 자동으로 검출하여 정상 인스턴스로 요청을 우회함.

### 6.2.2 Nginx 기반 다중 컨테이너 구동의 핵심 이점
- 무중단 배포 (Zero-Downtime Deployment): 신규 버전 배포 시 특정 애플리케이션 컨테이너를 정지하고 업데이트하는 동안, Nginx가 트래픽을 정상 구동 중인 타 컨테이너로 유연하게 중계 전달하여 사용자 서비스 중단 없는 롤링 배포 [^17] (Rolling Update)를 달성함.
- 프로세스 수준의 장애 격리 및 자동 우회 (Failover): 특정 애플리케이션 인스턴스에서 메모리 누수나 JVM Crash 장애가 발생하더라도, Nginx가 정상 컨테이너로 요청을 즉시 우회시켜 전체 시스템 셧다운을 방지함.
- JVM GC(Garbage Collection) 정지 시간 단축 및 자원 효율화: 초대형 단일 JVM 프로세스보다 적정 크기의 다중 JVM 컨테이너로 분산 구동함으로써 Garbage Collection에 의한 Stop-The-World 일시 정지 여파를 줄이고 멀티코어 CPU 자원 활용도를 극대화함.
- 클라우드 및 MSA 아키텍처 이관 사전 검증: 세션 정합성(Stateless Token, Redis 세션 등) 및 로드 밸런싱 환경을 단일 호스트 상에서 미리 구축하여 다중 노드 클라우드 환경으로의 이식을 사전 검증함.

## 6.3 Nginx 설정 파일(nginx.conf) 작성 및 업스트림 선언
- 프로젝트 루트에 Nginx 설정 파일(`nginx.conf`)을 작성하여 `upstream` 블록에 다중 Spring Board 컨테이너 서비스명을 선언함.

```nginx
events { worker_connections 1024; }

http {
    upstream backend-board {
        server board-app-1:8080;
        server board-app-2:8080;
    }

    server {
        listen 80;

        location / {
            proxy_pass http://backend-board;
            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        }
    }
}
```

- Nginx 설정 파일(`nginx.conf`) 핵심 구성 항목
  - `events { worker_connections 1024; }`: Nginx의 비동기 이벤트 처리 구조를 정의하는 컨텍스트 블록으로, 하나의 워커 프로세스(보통 호스트의 CPU 코어 개수만큼 생성됨)가 동시에 처리할 수 있는 최대 클라이언트 커넥션 수(1024개)를 지정함.
  - `http`: HTTP 웹 프로토콜 관련 전반적인 서버 설정(로드 밸런싱, 프록시 전달, HTTP 헤더 제어 등)을 총괄하는 최상위 컨텍스트 블록.
  - `upstream backend-board`: 백엔드로 트래픽을 중계 전달할 애플리케이션 컨테이너 그룹(로드 밸런싱 대상 서버 묶음)을 정의하는 블록으로, 도커 내장 DNS 서비스를 활용하여 동일 브릿지 네트워크(`board-net`) 상의 컨테이너 서비스명(`board-app-1:8080`, `board-app-2:8080`)을 직접 지정함.
  - `server`: 외부 클라이언트의 접속 요청을 수신하고 분산 처리 방식을 결정하는 가상 호스트(Virtual Host) 서버 설정 블록.
  - `listen 80`: Nginx 최앞단 프록시 서버가 외부 클라이언트로부터 HTTP 네트워크 요청을 수신할 수신 포트(80번 포트)를 지정함.
  - `location /`: 요청된 URL 경로의 루트(`/`) 이하 모든 HTTP 요청을 감지하여 내부 블록에 정의된 프록시 전달 규칙을 실행함.
  - `proxy_pass http://backend-board`: 수신된 모든 클라이언트 HTTP 요청을 앞서 `upstream`에 선언된 `backend-board` 애플리케이션 서버 그룹으로 중계 및 부하 분산 전달.
  - `proxy_set_header`
    - 요청을 백엔드 애플리케이션 컨테이너로 전달할 때 클라이언트의 실제 원본 요청 헤더 정보를 유실 없이 보존하여 전송하기 위한 설정 지시어.
    - `Host $host`: 클라이언트가 요청 시 사용한 원본 호스트 도메인 또는 IP 주소 정보를 보존하여 전송함.
    - `X-Real-IP $remote_addr`: Nginx 프록시를 거치기 전 실제 클라이언트의 원본 IP 주소를 보존하여 전송함.
    - `X-Forwarded-For $proxy_add_x_forwarded_for`: 거쳐온 모든 프록시 서버의 IP 주소 이력(Chain)을 덧붙여 백엔드 서비스로 전달함.

# 7. 클라우드 인프라 연동 및 마이크로서비스 아키텍처 확장

- 현대 클라우드 인프라 환경에서는 대규모 소프트웨어 시스템의 변경 이식성과 빠른 배포 속도를 달성하기 위해 마이크로서비스 아키텍처(MSA)와 컨테이너 기술을 결합하여 활용함.

## 7.1 마이크로서비스 아키텍처(MSA) 개념 및 구조

### 7.1.1 모놀리식(Monolithic) vs 마이크로서비스(MSA) 비교
- 모놀리식 아키텍처 (Monolithic Architecture)
  - 애플리케이션의 모든 기능(인증, 주문, 결제, 알림 등)이 단일 코드베이스 및 단일 실행 파일 형태로 통합되어 구동되는 구조.
  - 시스템 초기 개발은 용이하나, 서비스 규모가 확장될수록 일부분의 변경 사항으로 인해 전체 애플리케이션을 다시 빌드하고 재배포해야 하는 부담이 발생함.
  - 특정 모듈의 장애가 시스템 전체 장애로 확산되는 위험이 존재함.
- 마이크로서비스 아키텍처 (Microservices Architecture, MSA)
  - 하나의 대형 애플리케이션을 독립적으로 구동되는 소규모 서비스 단위로 분할하여 구축하는 시스템 아키텍처.
  - 각 서비스는 명확한 비즈니스 경계(Bounded Context)를 가지며, REST API [^10]<sup>2</sup> 또는 메시지 큐 [^18] (Message Queue) 기반의 가벼운 네트워크 프로토콜로 상호 통신함.

### 7.1.2 마이크로서비스의 핵심 설계 특징
- 데이터베이스 격리 (Database per Service): 각 마이크로서비스는 자신만의 전용 데이터베이스를 보유하여 서비스 간 데이터 종속성을 완전히 분리함.
- 폴리글랏(Polyglot) 구성: 서비스별 특성에 맞춰 최적의 언어, 프레임워크 및 데이터베이스(예: Java/Spring, Node.js, Python, Redis 등)를 독립적으로 선택하여 도입할 수 있음.
- 독립적 생성 및 라이프사이클 통제: 특정 서비스의 배포나 변경 작업이 다른 서비스의 운용에 영향을 주지 않음.

## 7.2 마이크로서비스 배포 단위로서의 컨테이너 역할

### 7.2.1 환경 격리 및 배포 이식성 확보
- 복수의 마이크로서비스가 요구하는 각기 다른 실행 런타임, 시스템 라이브러리 및 환경 변수를 컨테이너 이미지 단위로 완전 격리하여 환경 충돌을 방지함.
- 로컬 개발 환경, QA 검증 환경, AWS 클라우드 운영 환경 간 완벽한 이식성을 제공함.

### 7.2.2 장애 격리 (Fault Isolation) 및 독립 배포성 보장
- 개별 컨테이너 서비스 내부에서 메모리 누수나 예외 장애가 발생하더라도 타 마이크로서비스 컨테이너로 장애가 전파되지 않음.
- 장애가 발생한 특정 서비스 컨테이너만 손쉽게 재시작하거나 이전 정상 버전으로 롤백(Rollback)을 수행할 수 있음.

### 7.2.3 수평적 자동 확장 (Scale-out) 효율성 증대
- 시스템 전체 인프라를 증설할 필요 없이, 트래픽이 폭증한 특정 마이크로서비스(예: 이벤트 기간의 주문/결제 서비스) 컨테이너 인스턴스만 핀포인트로 복제 증설하여 자원 활용률을 극대화함.

## 7.3 컨테이너 오케스트레이션 생태계 개요

### 7.3.1 컨테이너 오케스트레이션 개념 및 정의
- 컨테이너 오케스트레이션(Container Orchestration)은 수십 ~ 수천 개에 달하는 수많은 컨테이너의 자동 배치, 스케줄링, 배포, 네트워크 생성, 부하 분산, 상태 감지 및 장애 복구(Self-healing) 등 컨테이너 전체 라이프사이클을 자동화하여 관리하는 원리 및 시스템을 의미.
- 오케스트라의 지휘자(Orchestrator)가 여러 악기의 연주를 조율하듯, 오케스트레이션 엔진은 클러스터 [^19] 내 여러 호스트 서버에 분산된 컨테이너들의 자원 할당과 실행 상태를 일관되게 총괄 제어함.

### 7.3.2 컨테이너 오케스트레이션의 필요성
- 수백 ~ 수천 개의 컨테이너가 수십 대의 노드 서버에 분산 운용될 경우, 자동 배치(Scheduling), 상태 감지(Self-healing), 롤링 배포 [^17]<sup>2</sup>, 로드 밸런싱을 수동으로 관리하기 불가능함.
- 서버 장애 발생 시 컨테이너 자동 재배치, 트래픽 급증 시 수평적 자동 확장(Autoscaling), 무중단 업데이트 등 고가용성 [^15]<sup>2</sup> (HA) 환경을 보장하기 위해 필수적.

### 7.3.3 주요 오케스트레이션 툴 및 AWS 관리형 서비스
- Docker Swarm: Docker 엔진에 기본 내장되어 별도의 외부 툴 설치 없이 다중 호스트 클러스터링 환경을 구축할 수 있는 경량 오케스트레이션 툴.
- Kubernetes (k8s): 대규모 컨테이너 자동화 배포, 스케줄링 및 관리를 위한 세계 표준 오픈소스 오케스트레이션 플랫폼.
- Amazon ECS (Elastic Container Service): AWS 인프라 환경과 강력히 통합된 관리형 컨테이너 오케스트레이션 서비스.
- Amazon EKS (Elastic Kubernetes Service): AWS 표준 인프라 상에서 순수 쿠버네티스 컨트롤 플레인을 완전 관리형으로 제공하는 서비스.
- AWS Fargate: 서버 인스턴스(EC2) 프로비저닝이나 관리 부담 없이 컨테이너 단위로만 자원을 할당받아 실행하는 서버리스 [^20] (Serverless) 컨테이너 컴퓨팅 엔진.

# 각주
[^1]: 이식성 (Portability): 소스 코드나 애플리케이션을 수정하지 않고 다른 운영체제나 인프라 환경으로 이관하여 즉시 실행 가능한 특성.
[^2]: 하이퍼바이저 (Hypervisor): 단일 물리적 컴퓨터에서 여러 개의 운영체제를 동시에 구동할 수 있도록 지원하는 가상화 관리 계층.
[^3]: 커널 (Kernel): 운영체제의 핵심부로서 하드웨어 리소스(CPU, 메모리, I/O 등)를 관리하고 시스템 호출을 처리하는 제어 프로그램.
[^4]: 에뮬레이션 (Emulation): 한 시스템의 하드웨어 동작 특성을 다른 소프트웨어를 통해 흉내 내어 실행하는 처리 가상화 과정.
[^5]: 베어메탈 (Bare-metal): 가상화 계층이나 하이퍼바이저 없이 물리적 하드웨어 상위에 운영체제가 직접 설치되어 동작하는 환경.
[^6]: CI/CD (Continuous Integration / Continuous Deployment): 지속적 통합 및 지속적 배포의 약어로, 코드 변경 사항의 자동 빌드, 테스트, 배포 과정을 통제하는 소프트웨어 개발 프로세스.
[^7]: 패키지 관리자 (Package Manager): 시스템에 필요한 소프트웨어 패키지의 설치, 업데이트, 의존성 관리 및 삭제를 자동화하는 유틸리티 도구.
[^8]: 소켓 (Socket): 동일 시스템 내 프로세스 간 또는 네트워크망을 통한 프로세스 간 통신의 연결 엔드포인트.
[^9]: 데몬 (Daemon): 사용자가 직접 제어하지 않고 백그라운드에서 상주하면서 특정 요청이나 시스템 이벤트를 처리하는 서비스 프로세스.
[^10]: REST API: HTTP 프로토콜을 활용하여 클라이언트와 서버 간 자원 및 명령을 주고받는 웹 응용 프로그램 통신 규격.
[^11]: 런타임 (Runtime): 프로그램이 실행되는 동안 동작하는 실행 환경 및 관련 소프트웨어 라이브러리 모음.
[^12]: Docker Swarm: Docker Engine에 내장되어 다중 호스트 환경의 컨테이너 클러스터링 및 오케스트레이션을 지원하는 기본 도구.
[^13]: 쿠버네티스 (Kubernetes): 구글이 개발한 오픈소스 기반의 대규모 컨테이너 자동 배포, 스케줄링 및 분산 오케스트레이션을 관리하는 표준 플랫폼.
[^14]: MSYS2: Windows 환경에서 유닉스 및 리눅스 전용 프로그램과 명령어(Git Bash 등)를 원활하게 구동할 수 있도록 지원하는 소프트웨어 호환 런타임 패키지.
[^15]: 고가용성 (High Availability, HA): 시스템이나 서버가 특정 장애 상황에서도 중단 없이 정상 서비스를 지속적으로 제공할 수 있도록 가용 상태를 높은 수준으로 유지하는 시스템 특성.
[^16]: 라운드 로빈 (Round Robin): 복수의 서버 인스턴스로 들어오는 클라이언트 요청을 별도의 우선순위 없이 입력된 순서대로 하나씩 공평하게 순환 분산하는 부하 분산 알고리즘.
[^17]: 롤링 배포 (Rolling Update): 기존 구버전 인스턴스를 한 번에 중단하지 않고, 신버전의 컨테이너 인스턴스를 하나씩 차례대로 교체하여 서비스 무중단 상태를 유지하며 업데이트하는 배포 전략.
[^18]: 메시지 큐 (Message Queue): 프로세스나 서비스 간 데이터를 송수신할 때 메시지를 비동기 방식으로 중계하고 임시 저장하는 미들웨어 버스 시스템.
[^19]: 클러스터 (Cluster): 여러 대의 독립된 컴퓨터(노드)를 네트워크로 연결하여 마치 하나의 거대한 단일 시스템처럼 작동하도록 묶어 놓은 집합체.
[^20]: 서버리스 (Serverless): 개발자가 물리/가상 서버의 프로비저닝이나 관리에 신경 쓰지 않고 애플리케이션 실행 단위에만 집중할 수 있게 지원하는 클라우드 컴퓨팅 모델.
